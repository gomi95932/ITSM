## 1. 使用与统计口径

支持组成员在“服务报表 → 通知健康”按支持组、INC/REQ、通知事件日期和投递状态查询。概况、原因分布和逐条明细用于发现未发送、失败及不确定结果，不提供批量重试或发送开关。现有受限通知工作台负责调查和授权重试。

- 样本日期使用 `outbox_events.created_at` 的上海日期，不使用工单创建日期或投递最近更新时间。开始与结束日期最多相隔 30 天，即最多覆盖 31 个自然日期。
- 责任归属使用工单**当前责任组**。转组后原组不再取得该工单的通知报表；目标组在当前权限内取得这些记录。这不是历史接收人、历史责任组或人员绩效归属统计。
- 一次通知事件可以展开成多条接收人投递；投递记录数、不同工单数和发送尝试次数分别计算，不可相互替代。
- 页面概况统计完整查询样本；投递状态筛选只影响原因分布和明细，不把筛选后的小样本冒充总体。
- `DELIVERED` 仅表示已有平台侧目标接收人发送确认，不表示员工已读、已接单或完成处理。`SIMULATED`、`SKIPPED`、`SENDING` 均不计入平台确认发送成功。
- “需要关注”包含 DEAD、REVIEW_REQUIRED、未知状态，以及带尝试或错误的 PENDING/SENDING。此指标不是失败率，也不覆盖所有长期滞留的干净待发送记录；须同时检查状态及事件时间。
- 覆盖量分别返回通知事件数、尚未展开事件数、已展开但无投递记录事件数。无接收人或策略不发送不能被包装为成功送达，也不能单凭这三项判断故障原因。

**重要边界：这里只统计当前投递状态，不是完整历史失败次数审计。** 人工重试沿用原投递 ID，并重置当前尝试周期及错误；后续成功可能不再出现在失败筛选中。保留的操作审计须结合调查使用，不应将当前快照当作整个生命周期的失败次数、历史失败率或供应商可用性报告。生命周期发送尝试事件账本不在本候选内。

## 2. API 与权限

`GET /api/v1/reports/notifications`

参数：必填 `groupId/from/to`；`serviceType` 为 INC/REQ，默认 INC；`state` 默认为 ALL，可选 ATTENTION、PENDING、DISPATCHING、SENDING、DELIVERED、SIMULATED、DEAD、REVIEW_REQUIRED、SKIPPED、OTHER。重复状态、未知状态筛选或无效日期拒绝，不自动放宽。

响应声明 `attribution=CURRENT_OWNER_GROUP`、`windowBasis=OUTBOX_CREATED_AT`、`timeZone=Asia/Shanghai`，并返回 `asOf`、`coverage`、完整 `cohortMetrics`、筛选后 `metrics/items`。

1. 认证后，在 REPEATABLE READ、READ ONLY 事务快照内重查在职状态、支持组启用状态和当前成员资格；无权查询返回 404。请求期间其他事务中的撤权不声称已经在既有快照内生效，下一次查询重新检查。
2. 先读取完整授权日期/组/类型样本，超过 5000 条投递时返回 503 `REPORT_NOTIFICATION_WINDOW_TOO_LARGE`，不返回截断明细或伪总数。即使再按 DEAD 等零匹配状态筛选，也不能绕过此上限。
3. 未知原始状态统一为 OTHER；错误只返回白名单分类，其他原始错误统一为 OTHER。接口不返回接收人员 ID/姓名、钉钉账号、任务 ID、接收人哈希、通知正文、payload 或厂商错误原文。
4. 明细仅含投递 ID、工单 ID/编号、事件/更新时间、当前状态、当前周期尝试次数和安全原因分类。工单详情入口继续经过既有详情授权，不用报表查询权代替操作权。
5. 此端点无写操作、无重试命令，不改变业务版本、工单状态或 SLA。
