# 服务目录组织方式调整：实现与验收记录

日期：2026-11-23

## 1. 本次执行范围

按确认后的范围调整服务目录组织方式，沿用现有配色、导航和服务卡片。保留原有“选择服务 → 填写报障 → 核对信息 → 提交”的流程，页面顶部“提交报障”入口继续使用原表单。

本次不引入智能推荐，不修改工单分类、审批、SLA、责任域、支持组、岗位任职或派单规则。不新增尚未准备好承接的业务服务，也不批量启用或停用已有服务。

此前两级、三级目录设计文档中的智能推荐、必须逐级选择、事项聚合等属于后续设计内容；本次以用户确认的窄范围为准，不将这些内容带入实现。

## 2. 员工端与管理员端

员工端“服务目录”增加分类筛选、关键词搜索，以及可选的子分类或业务系统筛选。默认显示“全部”，保留原有“故障与支持”“服务申请”和“暂未开放”分区。服务卡片按配置分组，点击后仍以原服务编码进入原表单。每次进入目录重新读取当前配置，无需重新登录。未发布服务继续隐藏；已发布但原流程尚不可用的服务继续不可点击；原有支持组、厂区可见范围继续生效。

管理员进入“服务组织 → 目录展示”，可为每个已有服务维护一级分类、可选二级分类及排序。对于应用系统，可组织为“信息化系统 → WMS系统 → 实际服务卡片”；服务卡片继续对应真实的INC/REQ编码，不创建虚拟工单类型。新建自定义服务未分类时进入“其他服务”，管理员再调整。

修改后填写变更依据，沿用现有内容确认控件，点击“保存目录展示”直接生效，并保留操作人、版本和时间。并发修改或编辑期间服务清单变化时拒绝覆盖，刷新后重新编辑。未保存时阻止切换其他配置页签，并提供撤销、刷新和离开页面提示。

目录展示页面同时列出“是否发布”“是否配置有效岗位映射”“是否有当前有效任职人员”。该提示不代表完整上线认证：钉钉消息可达、接收策略、主备响应、REQ审批配置等仍须按原功能核查。

## 3. 初始分类

| 既有服务编码 | 默认一级分类 |
|---|---|
| INC-PC、REQ-SOFT | 电脑与软件 |
| INC-NET、REQ-VPN | 网络与远程访问 |
| INC-MAIL、REQ-ACCOUNT | 账号与邮箱 |
| INC-BIZ | 信息化系统 |
| REQ-PERM | 账号与权限 |
| REQ-DEVICE | 设备与资产 |
| REQ-SHARE | 文件共享与存储 |
| REQ-GPU、REQ-AI | 算力与AI服务 |
| 其他自定义编码 | 其他服务，待管理员整理 |

默认分类仅用于展示。管理员可修改名称和归类，不依赖代码升级。业务系统权限服务也可按实际支持范围移入“信息化系统 → 对应系统”。不会根据服务名称猜测自定义编码的责任人或业务系统。

## 4. 先整理可承接服务，再逐步开放

首批核对已经建立的三类服务：Helpdesk、办公网络、信息系统维护。主备人员以管理后台实际配置为准，真实人员名单不纳入公开仓库。本次使用演示账号进行隔离测试，不将其视为已完成真实人员的在线核验。

管理员按以下步骤整理实际环境：

1. 在“目录维护”核对实际编码、名称、INC/REQ类型和发布状态，避免同一事项存在重复入口。
2. 在“服务映射”和“任职人员”核对支持组、岗位、有效人员及主备配置；使用现有预览分派能力确认候选人。
3. 在“目录展示”将上述可承接服务归入对应分类，并调整排序，使常用服务靠前。
4. 验证员工可见范围、必要字段、工单分派和通知；需要审批的服务核对原审批规则。
5. 其他服务先完成承接准备，通过现有“目录维护”发布，再维护展示分类。不要为了凑齐目录结构先开放空服务。

本次不自动变更既有发布状态，以免误停当前使用中的服务；目录展示也不增加独立的服务可用性开关。

## 5. 技术实现

新增不可变的`catalog_navigation_versions`展示版本表（迁移047），记录完整展示配置、管理员、变更依据及时间。原`service_catalog`、表单版本和服务组织版本不因展示调整而更新。

新增`GET/POST /api/v1/admin/catalog-navigation`，复用登录、CSRF、有效管理员校验和内容边界校验；保存采用版本比较及事务锁。员工仍通过原`GET /api/v1/catalog`获取服务，返回可选的`navigationPath`、`navigationOrder`展示字段。新增服务没有展示配置时使用默认分类，保持兼容。

前端复用`EmployeeForm`、`ServiceStructurePanel`及现有样式，新增`CatalogBrowser`和`CatalogNavigationPanel`。没有修改报障提交接口或引入模型调用。

## 7. 发布与现场验收

使用原GitHub CI、发布包及部署流程集中发布一次。部署前备份数据库并确认迁移047已包含在发布清单；目录展示API和前端必须与迁移一同发布。

发布后核对实际人员与服务配置，再用真实扫码登录检查员工目录、管理员保存、已有工单查询，以及首批三类服务的原报障提交。真实人员派单和钉钉通知验收仍按原方案执行。本次隔离测试不替代真实人员及钉钉闭环验收。

回退应用时保留新增展示版本表，避免删除审计历史。由于原服务编码、表单和派单配置没有变化，旧版本忽略展示表即可继续使用原服务目录。不要为回退执行删除表或回滚历史服务配置。
