## 0 阅读方式与决策摘要

本文是开发输入，不是产品宣传或部署完成证明。业务人员确认第 2、4、6、11、15 至 17 章的规则，开发人员按第 3、5、7、8、9、12、15 至 19 章拆分任务，测试人员按第 10、19 章验收。未确认的外部接口和现场参数必须保留适配器或配置项，不能在代码中猜测。

**首期决策**：自建轻量 ITSM 流程中台，钉钉 H5 为员工入口，PC 为 IT 工作台；工单、状态和 SLA 由 ITSM 唯一持有；钉钉 OA 仅负责需要审批的节点；GLPI/OCS/现有 CMDB 负责资产与配置项；Zabbix/ELK 负责监控与原始日志。先交付“报障 + 标准服务申请 + 分派处理 + 审批 + SLA + 知识 + 评价”的完整闭环，不复制卓豪 ServiceDesk Plus 的全部功能。

**V1.1 增补决策**：钉钉移动 H5 增加“语音一句话报障”，语音转写并抽取为可编辑工单草稿，经员工确认后才建单。该能力作为 MVP 文字入口稳定后的独立试点，不阻塞基础系统上线。完整开发契约与验收见第 14 章。

**已确认的执行顺序**：统一基线 → 安全入口保护、个人责任与 P1 确认 → REQ/OA 审批交付 → INC 收尾及知识评价 → 需求移交、监控试点 → PRB/CHG 等后续能力。监控接入及配置项（CI）关联第二期，完整安全事件（SEC）第三期。首期必须防止敏感内容在普通工单、附件、语音草稿、日志、消息和外部 AI 中扩散；无受控安全接收能力时，保留现有安全报告渠道，不开放敏感证据入口。详细任务与门槛见第 11.2 节。

**与前期建议的关系**：原规划 V1.1 建议新建流程中台，近期四台物理机规划将 ITSM 与 GLPI 分机部署。本版延续该落地假设。若当前 GLPI 已承载成熟工单，开发前必须做 1 周复用评估（支持钉钉免登、目录表单、审批/SLA、数据迁移及维护成本）；一旦选择 GLPI 为工单核心，应停用本版自建工单模块，不能两边并行维护同一工单。本版的接口与验收可继续作为选型评估清单。

**未决事项**：钉钉应用和 OA 接口权限；HR/AD/钉钉哪个字段为员工稳定 ID；CMDB 与 GLPI 的字段归属；服务时间与节假日；数据保留期；具体部署机资源；OA 审批模板；采购与权限服务的业务审批人。第 11 章列出默认值和确认门槛。

## 1 范围和产品原则

### 1.1 用户与任务

| 角色 | 首期入口 | 主要任务 |
|---|---|---|
| 员工 | 钉钉工作台 H5 | 文字/语音报障、申请、查询、补充、确认、评价 |
| 主管/系统负责人 | 钉钉 OA | 阅读申请上下文并审批，不在 ITSM 重复审批 |
| 一线服务台 | PC 工作台 | 队列接单、沟通、分派、SLA 跟进、知识复用 |
| 二线工程师 | PC 工作台 | 技术处置、协作、关联告警资产、提交解决方案 |
| 服务负责人 | PC 工作台 | 目录、分派规则、SLA、知识和质量复盘 |
| 平台管理员/审计员 | PC 工作台 | 身份与配置、集成失败处理、审计查看；权限分离 |

### 1.2 设计约束

- 普通员工首屏仅展示“我要报障”“服务申请”“我的工单”“知识搜索”；紧急故障入口可见但附电话和值班规则。报障必填不超过 4 项：问题描述、影响对象（可自动带出）、联系方式确认、附件可选。不要让员工填写技术分类、优先级、支持组、IP、MAC 或资产编号。
- 申请表仅显示该服务项需要的字段。表单提交后展示编号、预计处理时间、当前责任方和进度；钉钉消息入口直达工单。
- PC 工作台以紧凑列表和详情双栏为主：我的待办、组内未分派、即将超时、待审批/待用户、重大事件；支持过滤、搜索、批量分派（批量处理要逐单审计）。
- 以 ITIL 思路保留少而清楚的实践：事件快速恢复服务，服务请求标准交付，问题消除重复根因，变更控制生产风险，知识减少重复劳动。首期不引入复杂流程设计器、完整财务结算和多租户。
- 所有员工可看自己的工单；支持人员仅看授权组/服务范围；安全工单独立授权；经理仅看经过授权的部门汇总或脱敏明细。

### 1.3 首期与后续边界

| 阶段 | 实现 | 不在该阶段 |
|---|---|---|
| MVP | 钉钉免登、岗位与人员维护、目录、文字事件、标准请求、指派到人、评论附件、OA 审批接入、SLA、精准通知、知识检索、评价、审计、基础报表 | 自由编排流程、自动写 AD/ERP、生产变更自动化 |
| 语音试点 | 手机钉钉 H5 录音、转写、字段抽取、可编辑草稿、确认建单、降级回退 | 语音直接审批、授权或执行变更；未核实的机器人语音接入 |
| 第二期 | Zabbix 自动建单、GLPI/OCS/CMDB 设备关联、ELK 链接、AD 身份核对、AI 建议、问题及简版变更 | ITSM 直接调度 GPU、替换 SIEM/监控 |
| 第三期 | 权限自动交付、算力/AI 配额申请与到期回收、发布与安全事件、成本分析 | 自研监控、资源调度器或模型网关 |

上表为目标分期。资产/CI 字段、接口和安全权限矩阵的预留不代表首期开放相应功能；员工第一期仍可用文字描述影响对象。第二期监控先接可用性/性能告警，安全告警在第三期 SEC 隔离验收后接入，原安全响应机制持续有效。CI 指配置项，不是持续集成；ITSM 工程 CI/CD、备份和发布验证基础随首期建设，不属于第三期业务发布管理模块。

## 2 服务目录与业务规则

### 2.1 种子目录（配置数据，不写死为页面逻辑）

目录字段：`service_code`、中文名、责任域、关联业务系统（可空）、类别、描述、可见人群、默认支持组、处理岗位映射、表单模式、是否审批、SLA 策略、启用状态、版本。下列 12 项是最初试点建议，不是不可扩展的固定清单；以第 15.8 节用户确认的两大域和系统范围补充初始化模板。管理员可在 ITSM 内新增 INC 服务及标准 REQ、维护岗位和人员映射，经复核发布后生效；未验证目标接口的请求先按既定审批人工交付。

| 编号 | 服务项 | 类型 | 员工额外字段 | 审批/交付 |
|---|---|---|---|---|
| INC-PC | 电脑/外设故障 | 事件 | 设备自动选取、现象 | 无审批，服务台处理 |
| INC-NET | 网络/VPN 故障 | 事件 | 地点、现象、影响人数 | 无审批，网络组 |
| INC-MAIL | 邮箱故障 | 事件 | 故障时间、现象 | 无审批，协作组 |
| INC-BIZ | ERP/WMS/MES/SRM 故障 | 事件 | 系统、模块、业务影响 | 无审批，应用组 |
| REQ-ACCOUNT | 账号开通/调整 | 请求 | 目标系统、账号类型、用途、期限 | 主管与系统负责人；人工交付 |
| REQ-PERM | 业务系统权限 | 请求 | 系统、角色/岗位、用途、期限 | 主管和数据/系统负责人 |
| REQ-SOFT | 软件安装 | 请求 | 软件、设备、用途 | 依据许可风险审批 |
| REQ-DEVICE | 设备借用/领用 | 请求 | 设备类型、地点、期限 | 库存与主管规则 |
| REQ-VPN | VPN 开通 | 请求 | 用途、期限、目标资源 | 主管/安全规则 |
| REQ-SHARE | 共享目录权限 | 请求 | 目录、读写级别、期限 | 目录负责人 |
| REQ-GPU | GPU 算力申请 | 请求 | 项目、卡数/规格、期限、成本中心 | 资源负责人审批，首期人工交付 |
| REQ-AI | AI 模型/额度申请 | 请求 | 模型/用途、额度、期限、数据级别 | AI 网关负责人审批，首期人工交付 |

管理员发布目录版本后，**已提交工单保留表单版本和字段快照**；下线目录不删除历史。高风险权限、生产资源与敏感数据申请始终人工审批，禁止模型自行批准。

### 2.2 事件与请求区分

- 事件（INC）：非计划中断或质量下降；目标是恢复服务。相同故障可关联多个受影响用户，不要求每人独立处理一次。关联问题或变更不阻碍快速恢复。
- 请求（REQ）：事先定义且可重复交付的服务；可设审批、执行、验收步骤。审批拒绝形成终态 `REJECTED`；拒绝理由对申请人可见且敏感信息脱敏。
- 不把“申请账号”作为事件，也不把“现有账号不能登录”作为开通请求。首期用户只看到自然语言入口，后台由目录和人工复核纠正类型。

### 2.3 分派、优先级、升级

默认分派：已发布目录规则按服务、业务系统及厂区确定责任组和主办岗位 → 筛选有效任职员工 → 本人领取或受控指定候选并确认；未匹配进入服务台兜底队列。无已批准的主处理或值班规则时不启用自动选人。员工不选工程师，只上报影响与紧急事实，不能自行设 P1。规则或 AI 只提供分类建议，人工纠偏留痕。岗位、组、候选人与实际负责人分开保存，细则见第 15.8、16 章。

| 影响 × 紧急 | 高 | 中 | 低 |
|---|---|---|---|
| 全公司/核心生产 | P1 | P1 | P2 |
| 部门/重要业务 | P1 | P2 | P3 |
| 单个用户 | P2 | P3 | P4 |

P1 须值班主管确认，立即通知值班/负责人，建立重大事件记录（第二期可独立模块）；P2 组内升级；P3/P4 正常队列。安全事件另按数据敏感度和扩散风险分类，不默认进入普通服务台。

### 2.4 SLA 默认规则（试点值，必须经服务负责人确认）

| 优先级 | 首次人工响应 | 解决目标 | 日历 |
|---|---|---|---|
| P1 | 15 分钟 | 4 小时 | 7×24 |
| P2 | 30 分钟 | 8 个服务小时 | 工作时间 |
| P3 | 4 个服务小时 | 2 个工作日 | 工作时间 |
| P4 | 1 个工作日 | 5 个工作日 | 工作时间 |

工作时间默认周一至周五 09:00–18:00，时区 `Asia/Shanghai`，节假日来源为公司年度日历；上线前确认值班表。事件首次响应只在**真实人工回复或接单并发送消息**时完成，自动回复/机器人问候不算。解决目标在进入 `PENDING_CONFIRMATION` 时停止；用户重开后新一轮解决 SLA 单独计时，原轮不抹除。`WAITING_USER` 可暂停解决时钟，须填写问题与到期催办时间；`WAITING_VENDOR` 默认不暂停，特殊合同须显式配置。审批等待是否计入请求交付目标由服务项策略决定，试点默认暂停解决/交付时钟但不能暂停响应时钟；暂停理由必须保留。SLA 计算使用数据库 UTC 时间戳和版本化日历，变更日历不追溯改写已完成工单。

## 3 业务状态机与不可违反的不变量

### 3.1 工单状态

`NEW` → `QUEUED` → `IN_PROGRESS` → `PENDING_CONFIRMATION` → `CLOSED`。允许分支：`QUEUED/IN_PROGRESS` → `WAITING_APPROVAL` / `WAITING_USER` / `WAITING_VENDOR` → `IN_PROGRESS`；`PENDING_CONFIRMATION` → `IN_PROGRESS`（重开）；未执行前可 `CANCELLED`；审批拒绝 → `REJECTED`。禁止从 `CLOSED/CANCELLED/REJECTED` 直接修改为处理中，应创建新单并关联原单；重开仅在待确认期间。

| 动作 | 当前状态 | 目标状态 | 权限与约束 |
|---|---|---|---|
| 提交 | 无 | NEW | 员工本人/授权代报；事务内生成唯一编号、快照和事件 |
| 自动路由 | NEW | QUEUED | 规则执行；无匹配分派兜底组，不允许无归属 |
| 接单/回复 | QUEUED | IN_PROGRESS | 授权组成员本人领取或指定候选人确认，原子绑定唯一实际负责人；首响规则见第 16.4 节 |
| 发起审批 | QUEUED/IN_PROGRESS | WAITING_APPROVAL | 请求类且策略要求；只建一个有效审批实例 |
| 审批通过 | WAITING_APPROVAL | IN_PROGRESS | 验签回调、幂等；拒绝则 REJECTED |
| 需要补充 | IN_PROGRESS | WAITING_USER | 必须填写问题和截止时间，按策略暂停 |
| 员工补充 | WAITING_USER | IN_PROGRESS | 申请人或授权代报；恢复计时 |
| 外部协作 | IN_PROGRESS | WAITING_VENDOR | 供应商/外部任务编号、责任人必填 |
| 提交解决 | IN_PROGRESS/WAITING_VENDOR | PENDING_CONFIRMATION | 处理人填写解决摘要、分类和交付证据 |
| 确认/评价 | PENDING_CONFIRMATION | CLOSED | 申请人确认；72 小时无人确认可自动关闭并注明原因（试点值） |
| 重开 | PENDING_CONFIRMATION | IN_PROGRESS | 申请人说明未解决原因，生成新 SLA 轮次 |
| 取消 | NEW/QUEUED/WAITING_APPROVAL | CANCELLED | 本人且未交付；审批已发起须同步撤销或留待人工处置 |

不变量：每个工单一个当前责任组，最多一个已接单的个人负责人；候选接收人不是已负责人员。已受理工单的交接在目标人员确认前，原组及原人继续负责；未受理单由当前责任组负责。任何转派记录原组/新组、原人/新人及理由，SLA 不清零；协作者不自动取得解决或改派权限。审批未通过不可执行交付；外部执行成功不能仅凭 HTTP 200 判定，须核对业务结果；终态不可删除；状态、SLA、审计、outbox 同事务提交。消息失败不回滚工单。行政指派不等于审批通过或技术受理。

### 3.2 核心流程时序

1. H5 获取钉钉临时免登凭据 → 后端按官方授权流程兑换身份 → 关联稳定员工 ID、AD 登录名和在职状态 → 建立短期会话；不信任前端传来的员工编号。
2. 员工选择目录并提交 → 后端校验表单版本、可见性、重复提交键 → 事务内建单/分派/SLA/审计/outbox → 返回工单号。
3. 若需审批，后台任务以服务账号创建 OA 实例；返回 OA 实例 ID。回调必须验签、验时间窗口与事件 ID 幂等；仅把审批结果写回 ITSM 状态机。
4. IT 处理/用户补充/解决确认各生成事件，按订阅关系更新钉钉消息；通知失败重试，不影响工单真相。
5. 员工确认或 72 小时自动关闭；评价单独保存，关闭后仍可在规定窗口提交一次评价。

## 4 页面与交互规格

### 4.1 员工端（响应式 H5）

| 页面 | 最小元素 | 关键状态 |
|---|---|---|
| 首页 `/m` | 四个入口、我的待办数量、最近工单 3 条 | 免登失败明确重试与联系入口 |

## 5 技术架构与仓库结构

沿用原规划技术建议：Vue 3 + TypeScript + Vite、NestJS + TypeScript、PostgreSQL、Redis + BullMQ、对象存储（MinIO 或受控 NAS 对象接口）、Docker Compose；前端共用类型包。原则上一个后端服务和一个异步 worker，外部 API 统一适配层，不把接口代码写到控制器里。

```text
apps/web/                 员工 H5 与 PC 工作台，路由级权限
apps/api/                 NestJS REST API、身份、目录、工单、SLA、知识、审计
apps/worker/              outbox 投递、审批同步、通知、定时扫描、对账
packages/contracts/       DTO、枚举、OpenAPI 生成类型、错误码
packages/ui/              共用基础组件与表单渲染
infra/compose/            开发/测试 compose，生产环境变量示例（无密钥）
db/migrations/            版本化迁移与种子数据
tests/e2e/                Playwright 员工、服务台与审批假回调旅程
docs/                     ADR、数据字典、接口、运维、上线回退
```

后端模块：`auth`、`directory`、`catalog`、`ticket`、`workflow`、`sla`、`knowledge`、`attachment`、`notification`、`integration`、`reporting`、`audit`。模块通过应用服务和内部事件协作；只允许 `integration/adapters/*` 访问厂商 API。PostgreSQL 为事务真相，Redis 只做缓存/队列；Redis 丢失不可造成工单数据丢失，outbox 扫描可补投。附件只存对象 key、哈希、大小和权限元数据，禁用公开桶。

四台物理机建议与现有规划一致：1 号承载 ITSM，2 号 OCS/GLPI，3 号监控日志/算力控制面，4 号集中运维与备份；现场容量、备份目标和恢复演练独立验收。单机 Docker Compose **不是** HA，首期承诺可恢复而非自动切换。

## 6 数据模型与字段契约

## 7 API 契约与错误处理

统一前缀 `/api/v1`，JSON UTF-8，分页 `page/size`（size 最大 100）；写接口支持 `Idempotency-Key`（同主体、路径、请求体哈希 24 小时内返回原结果；键复用且载荷不同返回 409）；所有响应含 `requestId`，时间 ISO 8601 UTC。错误格式：`{code,message,requestId,details?}`；`details` 不含密钥、内部栈、用户隐私。401 未登录，403 无权，404 不可见资源，409 状态/版本冲突，422 校验失败，429 限流，503 外部服务不可用。

| 方法与路径 | 输入摘要 | 输出 / 验权 |
|---|---|---|
| `POST /auth/dingtalk/exchange` | `{authCode}` | 建立 HttpOnly Secure 会话；只允许服务端交换身份 |
| `GET /me` | - | 本人、组与可用角色，脱敏 |
| `GET /catalog` | `type,query` | 按身份可见的已发布目录 |
| `GET /catalog/{code}` | - | 当前版本 schema、服务说明、审批要求 |
| `POST /tickets` | `{serviceCode,formVersion,subject,description,impact,urgency,fields,assetRef?,attachmentIds?}` | 201 `{id,number,status,version}`；服务端计算 priority/group |
| `GET /tickets` | `mine/status/page/size` | 员工本人或授权组队列 |
| `GET /tickets/{id}` | - | 含角色过滤后的字段、时间线和 SLA |
| `POST /tickets/{id}/actions` | `{action,expectedVersion,comment?,reason?,targetGroupId?}` | 操作白名单；409 冲突；事务记录事件 |
| `POST /tickets/{id}/comments` | `{body,visibility}` | 员工不可写 INTERNAL |
| `POST /tickets/{id}/attachments/presign` | `{name,mime,size,sha256}` | 受限上传凭据；上传后查毒再可用 |
| `POST /tickets/{id}/feedback` | `{score,comment?}` | 仅本人且已关闭，可防重复 |
| `GET /knowledge` | `q,scope` | 仅已发布且有权查看 |
| `GET /reports/overview` | `from,to,group?` | 管理角色；口径与时区明确 |
| `POST /integrations/dingtalk/events` | 原始请求体 | 验签/时间窗/去重；仅记录受理后异步处理 |
| `POST /integrations/zabbix/events` | 外部事件 ID、主机、严重度、状态 | 服务鉴权；第二期 |

例：提交工单（响应模型仅示意字段，不是实际请求成功证明）

```json
{"serviceCode":"INC-BIZ","formVersion":1,"subject":"WMS 无法登录","description":"上午 9 点起无法进入系统","impact":"INDIVIDUAL","urgency":"MEDIUM","fields":{"system":"WMS","module":"登录"}}
```

行为细则：`POST /tickets` 的用户 ID、部门、服务项及审批策略从服务端解析；无法确认部门/主管时阻断高风险申请并提示人工补充；过期表单版本返回 `FORM_VERSION_CONFLICT`；员工查询他人工单应返回 404；回调即便同一事件重放 3 次也只推进一次；工单动作中的 `expectedVersion` 是必填乐观锁。

V1.2 新增管理与调度接口见第 16.6 节，沿用同一 `/api/v1` 前缀。`ACCEPT`、`REASSIGN`、`ACCEPT_HANDOVER` 等既有动作继续复用，不并行实现另一套工单状态接口；新增动作须先更新共享 DTO、状态转换、权限策略和测试。

## 8 系统集成契约与失败策略

| 系统 | 主数据方向与标识 | 首期动作 | 失败时行为 |
|---|---|---|---|
| 钉钉通讯录 | 钉钉 ID ↔ 员工 ID ↔ AD 登录名 | 免登、部门主管周期同步、离职停用 | 登录失败拒绝进入；同步失败保持最后快照并告警 |
| 钉钉 OA | 模板/实例 ID | 申请发起、审批回调和主动对账 | 回调无效拒绝；超时重试并查询状态，禁止猜测通过 |
| 钉钉消息 | `ticket_id + event_id + recipient` | 创建、转派、待补充、解决、超时通知 | outbox 指数退避，死信告警；不回滚工单 |
| OCS | 设备 SN/资产码 | 第二期读取本人设备清单；首期不开放设备关联 | 不可用时文字描述现象，不阻断报障 |
| GLPI/CMDB | 全局资产编号 + 外部 ID | 第二期只读资产/CI 关系快照；首期入口关闭 | 不可用时不创建伪资产，提示资产暂不可关联 |
| Zabbix | `eventid` / `triggerid` | 第二期事件去重、建单、恢复关联 | 重放按事件 ID 幂等，手工补录不复制事件 |
| ELK | 检索模板、事件 ID | 第二期保存受控检索链接，不复制原文 | 链接失效不丢工单 |
| AD/业务系统 | 稳定账号 ID、权限申请单 ID | 首期核对身份/人工执行；后续才写权限 | 自动写入失败不能标交付成功，须人工补偿 |
| 算力平台/sub2api | 申请 ID、资源/用户 ID | 首期人工交付，第三期可控 API 执行/回收 | 未获平台回执不标完成；不保存上游 Key |

每个适配器实现 `healthCheck, validate, send/query, reconcile`，凭据存受控密钥系统；配置请求超时、速率限制、重试上限和死信。重试只针对可重试错误；审批创建、资源交付等写操作须使用厂商支持的幂等键，若不支持则“查询现状后补偿”，不能盲目重复调用。对账每天执行，按外部实例状态修复内部待处理任务并记录审计，不自动覆盖已终结工单。

## 9 身份权限、安全与运维

### 9.1 权限矩阵

| 动作 | 员工 | 支持组成员 | 组长 | 目录管理员 | 审计员 |
|---|---|---|---|---|---|
| 看本人/授权代报单 | 是 | 按组 | 按组 | 不默认 | 按审计授权 |
| 看内部备注/处理日志 | 否 | 按组 | 按组 | 否 | 脱敏 |
| 接单/转派/解决 | 否 | 授权组领取及本人负责单，见第 15 章 | 仅本组管理范围，接管须理由 | 否 | 否 |
| 发布目录/SLA/路由 | 否 | 否 | 申请变更 | 是，双人复核 | 只读 |
| 查看安全事件 | 仅本人发起范围 | 独立安全组 | 独立安全组 | 否 | 按授权 |
| 重试集成/管理凭据 | 否 | 否 | 否 | 独立集成管理员 | 只读审计 |

请求对象的数据范围在后端每次校验，不能只隐藏按钮。第 15 章将上表“支持人员”细分为工程师、调度员、组长和服务经理；普通工程师不可因组内可读就替其他负责人处理。收到可信停用事件后应立即拒绝新操作并撤销会话，恢复作业将未结工单交回有效责任组及兜底负责人；外部离职同步时效须单独验收。不直接删除工单或审计。普通服务台不可查询全公司所有用户的权限申请和附件。管理员账号须 MFA/企业二次认证，供应商只可见授权的具体工单。角色调整和离职流程见第 15.4 节。

### 9.2 安全控制与运行基线

- 反向代理 HTTPS，钉钉回调验签、时戳、nonce/事件 ID 去重；会话 cookie `HttpOnly, Secure, SameSite`，需要 CSRF 防护；登录与写接口限流。
- 附件上传限制类型/大小（建议单文件 20MB，配置项），魔数校验、查毒、隔离；下载重新鉴权，签名链接短时有效。客户端与服务端均提示勿提交密码、密钥和涉密原文。
- 日志结构化输出到 ELK，必须有 `request_id/ticket_id/event_id`；健康检查区分 liveness/readiness；Zabbix 监控 DB/Redis/worker/outbox 堆积/回调失败/SLA 定时任务。
- PostgreSQL 一致性备份、附件备份、配置和密钥分开保管；备份异机保存，季度隔离恢复演练。RPO/RTO 上线前确认；单机故障不会自动切换。
- 测试数据脱敏；依赖锁文件、SAST、密钥扫描、数据库迁移预演和发布回退门禁。生产配置不包含真实 API Key 的明文示例。

## 14 钉钉语音一句话受理开发增补

### 14.1 入口、路径和边界

钉钉工作台 ITSM 微应用为唯一员工主入口：在手机钉钉 H5 的“我要报障”页，以麦克风图标提供语音快捷输入；其余目录、进度、补充、确认、评价继续使用同一 H5 与钉钉消息深链。PC 工作台保留文字录入，不将移动端录音接口推断为 PC 可用。机器人会话直接接收语音消息属于后续候选方案，只有在测试租户确认事件订阅、媒体权限、下载方式和合规后才实施。

执行顺序：`钉钉免登 → 本人在职校验 → 授权录音 → 停止录音 → 语音转写 → 脱敏与内容分级 → 智能体抽取字段 → 服务目录/权限/schema 校验 → 员工核对并编辑 → 点击提交 → POST /tickets → 工单号与消息通知`。若钉钉客户端转写已直接返回文字，客户端只提交文字到解释接口，不上传音频到 ITSM 后端。语音输入是填写表单的快捷方式，不是无需确认的自动派单渠道；分派、优先级、审批与状态仍由第 2、3 章的服务端规则决定。

示例：“我在三楼登录 WMS 失败，上午九点开始”。草稿候选：

```json
{"serviceCode":"INC-BIZ","summary":"WMS 登录失败","system":"WMS","location":"三楼","occurredAt":"2026-11-09T01:00:00Z","impact":null,"missingFields":["impact"],"confidence":0.84}
```

这里的时间是员工确认当天为 2026-11-09、时区为 Asia/Shanghai 时的示例；实际产品必须按会话日期和时区解析相对时间，并显示给本人确认，不可从模型输出直接认定事实。缺失字段用 `null` 和 `missingFields` 表示，禁止模型猜测影响人数或负责人。

### 14.2 页面状态与降级

报障页状态为 `IDLE → RECORDING → TRANSCRIBING → INTERPRETING → REVIEW → SUBMITTING → CREATED`，另有 `CANCELLED/ERROR`；录音中显示时长、停止和取消；草稿页同时显示可修改的转写原文、标题、候选服务、地点、发生时间和影响范围。低置信度（试点建议阈值 0.75，按真实样本校准）、服务目录多个候选、缺少必填信息时需要手动选定，不得自动提交。确认按钮只在校验通过时可用；提交时禁用重复点击，出错保留草稿。

录音权限拒绝、客户端不支持、录音中断、无网络、ASR 超时、模型异常、目录不匹配和身份失效时均提供文字表单，不丢用户已输入内容；会话失效需重新钉钉免登，不能以旧草稿绕开在职校验。电脑/非钉钉浏览器默认显示文字入口。无障碍用户可以完全不用语音完成同样流程。

### 14.3 适配层与 API

新增 `voice-intake` 模块，分开实现 `RecorderCapability`（前端钉钉环境探测）、`SpeechToTextAdapter`（官方能力或企业批准的受控 ASR）、`IntakeInterpreter`（结构化抽取）和 `DraftValidator`（目录、身份、表单规则）。优先验证钉钉官方移动端录音和转写能力；厂商能力、当前企业授权及客户端兼容须 PoC 实测，不在代码里硬编码未经验证的接口名。`sub2api` 只可处理经公司批准、已脱敏的文字抽取任务，不能假定它提供 ASR；涉密/客户敏感原文使用内网模型或纯文字手填。

在第 7 章统一 API 约定下增补：

| 方法与路径 | 输入/输出和校验 |
|---|---|
| `POST /api/v1/intake/voice/transcribe`（条件启用） | 仅官方客户端转写不可用且安全批准替代 ASR 时使用：本人会话 + 临时录音引用或受限上传；后端验证时长/大小/格式并限流；返回 `{draftId,transcript}`，不建单。官方转写可用时不调用本接口、不上传音频 |
| `POST /api/v1/intake/drafts/interpret` | `{draftId?,text}`；返回 `{draftId,serviceCode?,summary?,fields,impact?,missingFields,confidence,candidates?}`，只给本人已发布目录候选；纯文字可复用 |
| `GET /api/v1/intake/drafts/{id}` | 仅本人且未过期可取，其他人/过期返回 404 |
| `POST /api/v1/tickets` | 复用原接口，可附 `draftId` 仅作来源关联；用户确认后传修正值、表单版本与 `Idempotency-Key`；服务端重校验身份/在职/目录/字段/幂等，返回真实工单号 |

抽取器仅可输出约定 JSON schema 的候选，不可调用审批、权限分配、生产变更或消息群发工具。把语音转写视为不可信输入，模型输出再校验服务项白名单、目录可见性、字段长度/枚举、时间范围与置信度。语音说“帮我批准 ERP 管理员权限”只能形成待审批申请草稿，不得执行。错误码 `VOICE_PERMISSION_DENIED`、`ASR_UNAVAILABLE`、`INTAKE_LOW_CONFIDENCE` 和 `DRAFT_EXPIRED` 提示明确回退动作，不记录音频或完整转写到应用日志。

### 14.4 数据保护与集成失败

`intake_drafts(id,requester_id,channel,transcript_redacted,extracted_json,confidence,status,expires_at,confirmed_ticket_id?)` 只存脱敏短期草稿；本人可查，过期定时清理。**默认不持久化原始音频**；如转写接口必须暂存，仅用加密私有对象存储和短时受控访问，经安全负责人确认最短保留期、数据处理方及删除机制后启用。草稿的保存期、录音限时、用户告知与同意文案由安全/法务签字，不在开发时自行确定。审计只记录请求 ID、调用来源、耗时、结果码、本人确认时间和关联工单 ID；严禁将原始录音、完整转写、密码、Token、上游 Key 写入 ELK。

ASR/模型服务失败不影响文字入口，超时最多一次可控重试，未知提交结果先查幂等键/草稿关联而不盲目再次建单。供方服务、模型版本、路由配置和数据分类策略应可回滚；测评样本先脱敏，禁止用真实账号/凭据做提示词。业务系统信息与影响范围以员工最终确认内容为准。

T12 为语音试点切片：先用测试租户/真实手机验证录音、转写、免登授权及相关费用/配额；再用 fake ASR/解释器开发契约、草稿 UI、服务端校验和降级测试；经安全/法务批准数据路径后联调，10–20 名员工试点通过 A13–A16 后扩大。建议在基础 MVP 稳定后另排 1–2 周验证与开发，实际工期依接口权限和模型部署调整。若 PoC 失败，文字 H5 仍按 MVP 正常交付，不把机器人语音能力当作替代前提。

本增补为 V1.1 的优先适用条款；与第 1 章 MVP 表述不一致时，以“文字 MVP + 独立语音试点”的范围划分为准。官方钉钉开放平台能力需按项目实际开放权限与最新文档复核，不能把架构设计写成已完成集成。

## 15 工程师角色和人员维护

### 15.1 角色划分与责任边界

业务采用轻量 L1 服务台、L2 专业支持、L3 厂商协作模式；人少时一人可兼岗，但系统分别授予权限并保留操作身份。业务岗位、支持组、权限角色、当日值班分别配置：岗位定义做什么，支持组定义责任队列，权限角色定义能做哪些操作，值班定义何时由谁响应。不把“网络工程师”写成拥有所有网络单操作权的硬编码账号类型。

| 权限角色 | 责任与可执行动作 | 不默认拥有的权限 |
|---|---|---|
| 员工 REQUESTER | 本人报障、申请、补充、确认及评价；代报需有效授权 | 查看他人工单、内部备注、派单、执行审批 |
| 工程师 ENGINEER | 在授权组内领取；处理本人负责工单；发起交接；维护解决记录和知识草稿 | 替同组其他负责人解决、改 SLA、批准自己的权限申请 |
| 调度员 DISPATCHER | 指定范围内分类纠偏、未接单派人、追踪接收、催办和协调 | 修改全局角色、绕过审批、替负责人提交解决结果 |
| 支持组长 GROUP_LEAD | 本组成员维护提案、排班、升级、指派；经授权且说明原因后强制接管 | 其他组的管理权限、业务权限审批权、全平台审计导出 |
| 服务经理 SERVICE_MANAGER | 目录、服务承诺、路由和质量评审；处理跨组争议；批准本领域规则发布 | 直接读取全部敏感工单或执行生产权限变更 |
| 业务审批人 APPROVER | 仅按审批矩阵在钉钉 OA 审批；查看必要申请上下文 | 因“是主管”就成为 IT 工程师或获得任意工单可读权 |
| 平台管理员 PLATFORM_ADMIN | 身份映射、受控角色配置及系统参数；维护集成健康 | 默认读取所有工单正文、代替业务审批、无审计改库 |
| 集成管理员 INTEGRATION_ADMIN | 管理适配器、失败对账和获授权的消息重试 | 工单技术处置、角色自授予、读取密钥明文 |
| 审计员 AUDITOR | 授权范围内只读审计及脱敏报表 | 改派、接单、审批、配置写入 |
| 外部协作者 VENDOR | 首期由内部负责人代记外部任务和结果；以后按单授权 | 全组队列、内部全量备注、直接关闭内部工单 |

后台权限判定同时满足：在职有效、有效角色、角色作用域、组成员关系、工单归属或单单授权、当前状态、审批条件。拒绝优先；默认无权。平台管理员的配置权不等于所有业务数据可读权。紧急管理访问须限时、说明原因、独立复核及审计，不能成为日常越权通道。

### 15.2 专业支持组与责任样例

| 支持方向 | 典型服务 | 工程师责任 | 转交边界 |
|---|---|---|---|
| 服务台与桌面 | INC-PC、标准软件、外设 | 首问诊断、现场支持、沟通及基础恢复 | 网络、服务器、应用根因需指定二线接收 |
| 网络通信 | INC-NET、VPN、网络设备 | 网络连通性、无线、出口、网络服务恢复 | 申请新增权限仍走 OA；安全处置按受控渠道 |
| 系统与基础设施 | 服务器、AD、存储、虚拟化、备份 | 基础服务、容量、备份恢复和系统账号人工交付 | 高风险生产操作及权限扩大需相应授权 |
| 业务应用 | INC-BIZ，ERP/WMS/MES/SRM | 应用诊断、接口核对、业务恢复及厂商协调 | 业务数据修正或权限审批不得由技术岗自行批准 |
| 邮件与协作 | INC-MAIL、钉钉、共享协作 | 邮件和协作平台故障、标准交付 | 泄露、钓鱼或涉密证据交现有安全渠道 |
| 算力与 AI 平台 | REQ-GPU、REQ-AI、sub2api 故障 | 一期按已批准申请人工交付、核验和到期回收任务 | 不存上游 Key；三期才建设受控自动执行 |

安全负责人是一期敏感事项的受控交接联系人，不意味着一期建设完整 SEC 工作台。服务项须指定一名服务负责人、一个默认支持组及一个兜底组；每个启用组须有主组长、替补联系人和服务时间。未任命真实人员时保留“待确认”，不得生成虚构账号或默认所有人都是组长。

### 15.3 维护页面和增量数据模型

| 页面或实体 | 必须维护的数据与约束 |
|---|---|
| 支持组 `/admin/support-groups` | 组编码、名称、服务范围、厂区、服务日历、组长/替补、兜底组、启停及版本；不允许兜底循环 |
| 岗位与人员 `/admin/positions` | 岗位编码、名称、所属支持组、覆盖服务及厂区、职责；选择真实员工任职，维护主备、有效期、启停、复核状态及钉钉绑定健康；见第 15.5 至 15.7 节 |
| 工程师 `/admin/engineers` | 引用 `employees.id`，展示部门/在职状态、组及专业技能、可接单状态、有效期；不另建登录账号 |
| 角色授权 `/admin/role-bindings` | 固定角色模板、授权对象、组/服务/厂区作用域、有效期、申请/复核人、撤销原因及版本；一期不做自由权限设计器 |
| 值班 `/admin/duty` | 成员、时间段、时区、替补及生效状态；与休假/停用校验；无排班时只能人工兜底 |
| 路由 `/admin/routing` | 条件、目标组、优先顺序、分派方式、候选条件、接收时限、升级链；草稿、预览、复核、发布、停用 |

沿用 `employees`、`identity_links`、`support_groups`、`group_memberships`，不改写已有主键或历史迁移。新增设计表 `role_bindings` 保存角色及作用域；`engineer_profiles` 保存非鉴权专业资料；`duty_shifts` 保存排班；`routing_policy_versions` 保存不可变路由版本。权限模板先用受控代码枚举，不新增过度通用的权限平台。现有 `priority_reviewers` 仍作为过渡授权源，迁移须显式映射、双读比对后切换，不能因发放组长角色就悄悄增加 P1 确认权限。

`role_bindings` 最小字段：`id,employee_id,role_code,scope_type,scope_id,valid_from,valid_to,status,requested_by,reviewed_by,revoked_by,reason,version`；同主体/角色/范围不允许重叠有效授权。角色与成员关系分别校验，调度资格不能被专业技能字段替代。组长只能提案或维护授权本组范围，不可修改自己的高权限角色。特权授权和路由发布须不同人员复核；紧急撤权立即生效后补复核，不为双人审核延迟止损。

### 15.4 入转调离和日常维护

1. 初始化：确认员工稳定主键，通讯录导入在职人员；钉钉企业 ID 与用户 ID、AD 不可变对象标识分别映射员工。姓名、手机号及可改登录名不作为跨系统唯一键；冲突进入人工核对，不自动合并。
2. 入组授权：组长选择现有员工及专业方向，提交组成员和角色作用域；有权限且非申请人的复核者确认后生效。初始特权账号由项目负责人受控引导开通并留审计，禁止公开注册管理员。
3. 转岗或休假：新增授权与旧授权撤回分开记录；休假只改变可接单状态，不默默移交在办单。离岗前逐单交接，未接收项进入组长待办；跨组转岗不保留无依据的历史读取权。
4. 离职停用：可信来源同步成功后即时标记停用、拒绝 API、撤销会话及过期角色；恢复作业处理其在办单、待交接、审批和到期回收任务。保留业务状态、SLA 和审计，通知本组及兜底负责人。不可直接删账号、工单或历史姓名快照。
5. 例行核查：每日对账身份异常与无负责人组；每月由组长复核人员及在办单；每季度复核特权和越组授权。以上频率为建议配置，审批后启用并记录执行结果。

通讯录回调结合周期全量/增量对账，处理丢事件；同步失败告警并展示最近成功时间。不能因为来源不可达而把人员批量判定离职；无新鲜有效身份依据时阻断新特权授权及高风险交付。临时人工停用可立即执行。外部停用检测时延与 ITSM 内部恢复时延分别度量，不声称已完成自动离职集成。

停用组或移除最后一名有效成员/组长前，须评估开放工单、目录、审批及回收任务。普通调整无有效接替方时拒绝保存；紧急停用人员不受此阻断，系统原子记录兜底任务并升级至受控服务台。历史审计访问按当下权限重新判断。

### 15.5 一期岗位与人员管理

本节为一期必交范围，归入 BASE-01、P1-02 和 P1-10，不延至二期。维护入口统一命名为“岗位与人员”，使用岗位列表与任职人员明细，不建设复杂 HR 或通用 IAM 系统。普通员工建单时不选择技术岗位或处理人，仍由目录和规则完成分流。

| 对象 | 含义及示例 | 与其他对象的关系 |
|---|---|---|
| 业务岗位 | 桌面支持、网络运维、系统运维、ERP 运维、WMS 运维、邮件协作、AI 网关运维 | 岗位归属一个支持组，可覆盖多个获批准的服务项；跨组兼岗通过多条任职维护 |
| 任职员工 | 该岗位的实际在职人员，不是“网络管理员”共享账号 | 一岗可多人，一人可多岗；每条任职有责任范围、主备、有效期和状态 |
| 钉钉身份 | 员工在目标企业内的身份映射 | 沿用 `employees.id → identity_links(corp_id,ding_user_id)`，不以姓名或手机号代替 |
| 权限角色 | 工程师、调度员、组长、管理员等受控操作资格 | 岗位不自动授予管理权；同组有效成员及所需权限仍需独立验证 |
| 工单负责人 | 工单当前唯一负责的实际员工 | 岗位多人不等于多人共同负责；候选确认前不能伪造本人已接单 |

管理员在页面中创建岗位并配置支持组、服务及厂区；有本组维护权限的组长从受信通讯录中检索员工，提交任职及主备配置，由不同且有权限的人员复核生效。页面展示姓名、部门、在职状态、钉钉绑定是否有效、应用可见范围核验结果和最近同步时间；同名员工用部门及受限员工标识区分。不得让前端手工填写任意钉钉 userId 冒充选人。

岗位基础配置包含编码、名称、职责、所属支持组、服务/厂区范围、启用状态和版本。任职配置包含员工、岗位、主岗/兼岗、主处理/替补、有效起止、可接单状态、提案及复核信息。主岗/兼岗仅用于管理展示，不改变鉴权；主处理/替补用于路由优先级。相同岗位、服务、厂区及重叠有效时段内，不允许出现互相冲突的主处理配置；存在多名合格人员但无唯一主处理时，转人工选择，不按姓名顺序或随机选人。

选择员工后复用其已有身份映射；未绑定、冲突、停用、失效或未能核验企业应用可见范围时，界面明确显示问题及处理入口。可以保存草稿，不允许发布为该岗位的有效钉钉接单联系人。不得因此阻止普通员工报障：无合格联系人时工单进入可见的待分派队列，由独立配置的有效调度/兜底联系人接管。企业应用凭据只在服务端受控保存，管理页面不显示密钥。

岗位任职、支持组成员资格和权限角色是分别审计的配置，不隐藏联动授权。页面可提示缺少组成员或操作资格，并串联已有受控提案流程；未全部满足前不进入可派单候选集合。日常新增及提权须独立复核，提案人和任职对象均不得复核自身任职；紧急停用即时生效，不为复核延迟止损。

### 15.6 数据与接口实施契约

下列是待实现的增量设计，不是现有数据库或已上线 API 清单。沿用员工、钉钉身份、支持组和角色实体；新增迁移，不修改历史迁移，不另建一套钉钉账号。

| 实体 | 最小字段与约束 |
|---|---|
| `support_positions` | `id,code,name,group_id,description,status,version,created_by,updated_by`；编码唯一，已被引用的岗位不可硬删除 |
| `position_service_scopes` | `id,position_id,service_code,site_scope,responsibility_kind,version`；支持服务与岗位多对多，区分主办/协办；只能引用获授权服务/厂区，拒绝重叠主办冲突；不以逗号字符串保存服务集合 |
| `position_appointments` | `id,position_id,employee_id,appointment_type,responsibility_type,valid_from,valid_to,status,requested_by,reviewed_by,revoked_by,reason,version`；同岗位同员工不允许重叠有效任职 |
| 任职责任范围关联 | 将任职关联到岗位服务范围；主备冲突按明确范围和有效时间检查；组、岗位、服务、任职及员工停用均使候选失效 |
| 身份映射及健康 | 复用 `identity_links`；同步/可见范围核验时间、结果和错误单独受控记录；身份变更审计，不将 userId 复制为任职主键 |
| 分派与通知证据 | 分派记录保存岗位、任职、规则版本及员工 ID 的决策快照；发送尝试保存实际企业/接收人映射版本、厂商任务及结果；身份明细仅授权运维可读 |

任职状态为 `DRAFT/PENDING/ACTIVE/REJECTED/REVOKED`，有效性同时由状态、起止时间及实时人员资格决定；过期无需等定时任务才失权。修改有效任职形成新提案，复核前旧版本继续按原有效期生效；即时撤销例外。主备冲突校验、复核、成员调整及工单动作使用一致锁顺序或等价串行化策略，避免并发发布两个主处理或撤权后仍接单。复用既有审计基础记录前后值、实际操作者及原因。

| 方法及路径 统一前缀 `/api/v1` | 输入及边界 |
|---|---|
| `GET /admin/positions`；`GET /admin/positions/{id}` | 按作用域返回岗位、任职和绑定健康；敏感身份标识按权限最小展示 |
| `POST /admin/positions/proposals`；`POST /admin/positions/proposals/{id}/review` | 创建/修改/停用岗位或范围的受控提案及独立复核；更新带 `expectedVersion,reason,idempotencyKey` |
| `GET /admin/directory/people` | 受限搜索受信员工目录；不接受客户端自称的操作者、在职状态或映射关系 |
| `POST /admin/position-appointments/proposals`；`POST /admin/position-appointments/proposals/{id}/review` | 提交岗位、员工、范围、主备及有效期，复核时重新校验身份、成员和冲突 |
| `POST /admin/position-appointments/{id}/revoke` | 有权人员即时撤销；检查及恢复待接收、在办单和未结任务，不硬删历史 |
| `GET /admin/positions/{id}/eligible-assignees` | 按服务、厂区和当前时刻返回可派单人员及失效原因；不因可被检索就授予读单权 |
| `POST /admin/positions/{id}/routing-preview` | 给出岗位、候选、主备、兜底及命中版本；预览不建单、不发消息、不改变权限 |

DTO 在共享 contracts/OpenAPI 登记，采用字段白名单；写接口验证会话、CSRF、作用域、版本及幂等。身份未绑定、主处理冲突、任职失效分别返回可定位的错误码；无权对象按不可见策略处理，不向任意用户泄露人员目录或钉钉标识。

### 15.7 钉钉身份维护与任职变更

优先以经授权的钉钉通讯录同步和周期对账维护人员；真实权限未具备前，可由管理员采用受控导入及双人核验建立映射，禁止按显示姓名自动认领账号。相同企业内的一个钉钉用户只能对应一个员工，一个员工也不得并行绑定多个有效钉钉用户；跨企业映射必须显式选择企业，不能使用个人侧提供的其他企业身份替代。

转岗、任职到期及日常移除前展示在办单、待接收、审批与回收责任影响，并要求明确接替或兜底。撤销任职后不得继续接受该岗位的新工单或旧候选；待接收进入恢复队列，在办单按受控交接处理，不静默改写原负责人或延长 SLA。若员工仅失去一个岗位而仍持有其他岗位，不能误停用其所有身份；同样不能因仍在同一组就绕过被撤销岗位的路由限制。工单保存分派依据，对岗位撤销后的继续处理采用显式、有审计的逐单授权或交接，不自动保留原岗位授权。

可信离职或安全紧急停用立即阻断登录、接单及后续通知，恢复作业分配未结责任；已有日志保留历史任职和姓名快照。身份映射变更后，尚未发送的消息重新校验当前映射及授权；厂商已受理但结果未知的任务先按原任务对账，不能改目标后盲目重发。不得把目录暂时不可达当作全员离职。

### 15.8 两大运维域及服务目录岗位人员自主配置

用户确认的管理结构为“责任域 → 服务分类/业务系统 → 服务项 → 主办岗位及可选协办岗位 → 任职员工 → 企业钉钉身份”。前两层用于目录组织及统计，不等同于鉴权支持组；实际工单仍有唯一责任组和个人负责人。一个服务项可按厂区等明确条件关联多个岗位，一个岗位可负责多个服务；一个岗位可有多名任职员工，一人也可兼多个岗位。主办规则在相同有效条件下必须唯一，协办岗位不会因此获得所有相关工单正文或成为共同负责人。

以下是初始化模板，不是自动启用的真实服务，也不代表新增部门编制。岗位名称、服务分类、系统名称、支持组和员工主备均可在后台调整；HUB、TB 的含义和实际服务范围由业务负责人维护。

管理端采用两个相互跳转的轻量页面，不建设流程设计器：

1. “服务目录”按责任域及系统展示列表，支持创建、编辑、排序、停用和搜索；服务项维护类型、可见范围、受控表单模板、SLA、审批策略、主办岗位、可选协办、厂区和兜底。新增业务系统或 INC 服务不是只修改已有 REQ 策略，也不能要求改种子 SQL。
2. “岗位与人员”维护岗位、所属支持组、职责、覆盖服务及任职员工。支持从岗位反查服务，也能从服务跳转岗位选人；人员来自受信钉钉目录/已核验映射，展示主备及有效性。
3. 配置变更先保存草稿，再预览“该服务会进入哪个组、哪个岗位、哪些有效人员、通知谁、无人时谁兜底”。复核人确认后发布一致的版本组合，不允许目录已更新而路由仍指向旧岗位的半发布状态。
4. 日常换人只维护岗位任职，不逐个修改所有服务项；新增服务只关联已有岗位，不复制员工名单。对多个服务的影响在发布前列出，未结工单不被静默改派。

数据实现复用 `service_catalog`，增量增加责任域和可空的业务系统引用；新增轻量 `service_domains(id,code,name,status,version)`、`business_systems(id,code,name,domain_id,status,version)` 管理目录分类。系统目录只保存识别和责任元数据，不保存生产账号密码，也不是 CMDB 副本。责任域、业务系统及岗位编码稳定、名称可改；停用保留历史引用，已引用对象不可硬删除。新增服务采用受控类型枚举、表单模板及已有审批/SLA 策略，不允许上传脚本或绕过 REQ/OA 门槛。

服务与岗位关系以 `position_service_scopes` 为统一关系源，已发布路由版本引用对应关系版本；不得再分别保存互相覆盖的“服务绑定人员名单”和“岗位绑定服务名单”。有效路由同时绑定目录、岗位范围和人员资格；发布校验目标岗位在相应支持组有资格承办，跨组协办需显式范围和逐单协作授权。新增目录/岗位/映射在一次数据库事务内发布，或采用等价的不可变配置包切换；重试不能形成重复服务或部分发布。

补充管理接口统一前缀 `/api/v1`：`GET /admin/service-domains`、`GET /admin/business-systems` 返回授权目录；相应创建/修改/停用采用受控提案及独立复核。`POST /admin/service-catalog/proposals` 和 `POST /admin/service-catalog/proposals/{id}/review` 覆盖新增/更新/停用服务及岗位映射；REQ 的审批策略复用已有目录版本机制，不建设旁路。`POST /admin/service-catalog/routing-preview` 使用草稿和样例预览完整候选链，不发消息。实现时逐项登记精确 DTO、作用域、版本和幂等；接口名称为设计契约，不能作为已经上线的证明。

一期验收必须由获授权业务管理员仅使用页面完成“新增一个业务系统及服务 → 关联岗位 → 选择真实任职员工和钉钉身份 → 复核发布 → 员工报障 → 指定人收到通知并处理”，全程不修改源代码、种子数据或手工改库。不要求开发者提前硬编码全部系统，通知和审批仍受真实企业应用权限约束。

## 16 从工单到人及处理闭环

### 16.1 分派规则

员工提交描述后，由服务端依据已发布服务目录、厂区和可见范围确定支持组。路由按显式优先级执行，冲突在发布时检查；同优先级多条匹配不得随机选人，转人工兜底并记录冲突。工单保存路由版本、匹配原因及责任组快照，后续规则更新不自动改派历史单。

一期完整路由为“服务/厂区 → 支持组及处理岗位 → 当前有效任职员工 → 唯一候选人 → 本人确认后的实际负责人”。已配置岗位的服务，只允许符合该岗位范围、有效任职、组成员及操作权限的人员领取或被指定；例外协作/接管必须按受控动作显式授权并审计。未匹配岗位进入人工兜底，不静默放宽为任何同组人员均可处理。

首期提供两种方式：合格任职人员从岗位队列领取；调度员或组长从服务端返回的候选名单中给未接单指定一名具体员工，待其确认。配置且复核了唯一主处理人时，可按受控规则优先向其发出接收邀请，失效时查找明确替补；这不等于自动接单。自动按轮班或负载选人是可选增强；技能只做候选过滤，负载算法不引入黑箱 AI。任何方式都不得分给停用、任职失效、非授权组成员、钉钉身份无效或明确不可接单人员。

兜底顺序为本组调度员/组长 → 已配置替补 → 服务台兜底组/服务经理；各层为确定的在职联系人或受控值班入口。无有效候选时建单仍可成功，但必须可见地处于“待人工分派”，产生兜底待办和通知失败告警，不能显示已交给某人。严禁为消除红色积压而将所有人设为负责人。

### 16.2 唯一负责人和交接动作

| 情况 | 操作与结果 | 责任保持 |
|---|---|---|
| 未认领 | `ACCEPT` 原子领取，校验在职、组、版本及幂等 | 成功者成为唯一负责人，其他竞争者返回 409 |
| 调度员指定未接单人员 | 新增 `ASSIGN_OFFER`，写入候选人及截止时间；候选人确认后才受理 | 确认前仍由当前组承担责任，不计为已接单 |
| 同组或跨组移交 | 复用 `REASSIGN`，指定目标组、在职成员及原因 | 确认前原组和原人继续负责；仅目标个人获该单必要可见性 |
| 接收交接 | 复用 `ACCEPT_HANDOVER`，原子切换组和人 | 原业务等待状态不变；仅原 QUEUED 转 IN_PROGRESS |
| 拒收或撤回 | `DECLINE_HANDOVER` 或 `CANCEL_HANDOVER`，记录理由 | 原负责人不变；未接单仍回原队列；提示调度员处理 |
| 超时 | 作业标记候选过期并升级，只通知一次同级超时事件 | 不清空仍有效的原负责人、不重置 SLA、不无限循环改派 |
| 强制接管 | 新增 `FORCE_TAKEOVER`，组长/服务经理在授权范围内指派有效人员并必填原因 | 事务切换并通知双方；特殊管理动作，不伪造接收人已操作 |
| 人员失效 | 清除无效个人和待交接引用，恢复到有效组待人工认领并升级 | 保留原业务状态和 SLA；原组也无效则使用受控兜底组 |

新增动作是待开发契约，不表示当前接口已接受。候选一旦生成，普通领取须遵守预约：仅候选人确认、授权调度员撤回/改派或到期解除；不得一边显示“已派张三”一边让李四无提示抢走。强制指派立即形成真实责任，但必须显著显示为管理指派并催促本人确认知悉；知悉超时继续升级，不伪造首响或本人已接收。紧急情况下无有效人员仍升级主管，不指定失效账号。

协作采用一名主负责人加若干按单授权协作者：协作者只能读取必要上下文、添加允许范围的记录及协作结果，不能默认解决、改派、读全部附件或审批。首期外部协作只记录供应商任务编号与内部联络人，ITSM 内部负责人持续承担跟进责任。

### 16.3 接收时限与升级

以下为待批准试点参数，不是现有 SLA 承诺；接收计时独立于首次响应和解决时钟。P1 候选即时通知并启动响应，不等主管确认或接单超时。

| 优先级 | 候选接收或交接提醒时限 | 使用日历 | 到期动作 |
|---|---|---|---|
| P1 | 5 分钟 | 经确认的 7×24 值班 | 即时通知主备值班；5 分钟未接收升级主管并电话兜底 |
| P2 | 15 个服务分钟 | 服务日历 | 组长检查并派备份人员 |
| P3 | 60 个服务分钟 | 服务日历 | 调度员催办，组长待办 |
| P4 | 240 个服务分钟 | 服务日历 | 调度员处理并提示后续风险 |

每次交接等待窗口取配置时限与剩余首响/解决预算的较短值；已违约则立即升级，不能以改派延长承诺。提醒层级有上限和去重键；到最终层仍无人响应时持续显示红色未受理，并走批准的电话/值班机制，不自动标记已处理。无真实 7×24 人员和电话联系人时，P1 能力标记未具备，不假定 IM 送达等于有人值班。

### 16.4 处理记录与员工反馈

工程师受理后在 PC 或钉钉 H5 同一工单内补充诊断，记录公开进展或内部备注；请求员工补充要填写问题及截止时间；外协要填厂商、任务编号及内部负责人；解决要填原因分类、处理摘要、验证结果和必要脱敏证据。权限申请执行前重新核对有效审批、申请范围及复核要求，技术接单不代表可以提前交付。

`accepted_at` 记录个人受理；首次响应仅在真实人工回复已在员工可见时间线持久化、且可由本人查询时计入，或按已批准策略以人工受理通知的真实送达为依据。自动回执、系统派单、模拟消息、主管强制指派及未送达消息均不计。两种合格证据取最早一次并保存 `response_evidence_id`；SLA 策略须明确采用哪种，未批准策略前沿用现有实现，不私自变更历史指标。

解决后进入待员工确认，员工在平台或钉钉 H5 确认、评价或说明未解决并重开。自动关闭必须依据 `resolved_at` 或专用 `confirmation_started_at`，不能用会被备注、交接或通知更新的 `updated_at`。重开创建新 SLA 周期，历史不覆盖。外部交付待复核、尚待审批或证据不全时不能“提交解决”绕过门槛。

### 16.5 增量字段及一致性

沿用 `tickets.owner_group_id/assignee_id/pending_group_id/pending_assignee_id`。新增候选字段 `assignment_kind,assignment_offered_at,assignment_due_at,assignment_policy_version_id,assignment_state`；唯一活动候选约束由行锁及状态检查保障，必要时用独立 `ticket_assignment_offers` 表保存历史。增加 `ticket_collaborators` 和受控 `escalation_events`，复用 `ticket_events/audit_logs/outbox_events`，不新建第二套时间线。

业务状态与分派状态正交：等待用户、等待审批、外协等业务状态不因换人重置。领取、候选接收、管理接管、离职恢复均锁定同一工单行，验证 `expectedVersion`，同事务更新归属、时间线、审计和 outbox。授予/撤销角色、移除成员与工单写操作需采用一致锁顺序或等价串行化策略，防止已移除人员在竞态窗口接单。

定时扫描采用有界批量、租约或跳过已锁行；幂等键绑定主体、动作、实体与请求哈希。重复同载荷返回原结果前仍重查当前可见权限；同键异载荷 409。审计包括实际操作者、渠道、来源/目标组与人、理由、规则版本、时间及请求 ID，不允许前端冒充系统操作者。

以下统一前缀 `/api/v1`；路径不重复前缀。现有只读组接口可复用，但仅提供获授权的路由目标最小目录，不能由此取得全部组工单或成员隐私。新接口逐项在共享 contracts/OpenAPI 登记，本文不是已上线接口清单。

| `POST /admin/role-bindings/{id}/revoke` | 获授权管理者即时撤销；撤会话/缓存并触发未结事项恢复 |
| `POST /admin/duty-shifts`；`PATCH /admin/duty-shifts/{id}` | 范围内排班；检查重叠、停用人员及替补 |
| `POST /admin/routing-policies/{id}/publish` | 发布已复核版本；提供样例命中预览和兜底检查 |
| `POST /tickets/{id}/actions` | 复用现有入口；新增动作有 `action,expectedVersion,targetGroupId?,targetAssigneeId?,reason?` |

实际 PATCH 路径应包含实体 ID；创建、提案、复核及发布的 DTO 分开，禁止任意字段批量写入。控制器调用同一权限与领域服务，PC、H5、自动作业不能分别写不同业务规则。业务冲突使用明确代码，如 `ASSIGNMENT_CONFLICT`、`NO_ELIGIBLE_ASSIGNEE`、`HANDOVER_EXPIRED`、`ROLE_SCOPE_DENIED`，对无权对象仍按不可见策略返回 404。

### 16.7 业务样例与责任统计

以下姓名仅为验收样例，不是实际任命：管理员配置应用支持组的“WMS 运维”岗位，已核验钉钉身份的李四为主处理、赵六为替补，分别完成有效任职及所需授权。员工张三从钉钉报告“WMS 无法登录”，系统路由该组及岗位；调度员或已复核规则选定李四为候选，工作通知发送到李四的企业钉钉账号，李四在 H5 确认后成为负责人。若初查是网络故障，李四发起给网络运维岗位合格人员王五的交接，王五确认前仍由李四跟进。王五接收并恢复后填写公开解决摘要，张三在钉钉确认，PC 时间线同步显示全过程；李四无效或超时按明确替补/兜底规则处理，不因同岗位多人而给每个人标记负责人。

报表按支持组、实际负责人、服务、厂区统计待接收、在办、超时、交接次数、首响和解决达标、重开、满意度及通知失败。审计保留各责任区间，不能把工单最终解决人的姓名回填为全过程负责人。超时按总服务承诺计算，再展示各组/人的占用区间和等待原因，不因转派清除违约；数量和工时需结合难度及协作，不把单量直接当作绩效结论。

## 17 平台与钉钉双入口

### 17.1 首期交互路径

推荐首期采用“钉钉工作通知 → 企业免登 H5 → 同一 ITSM API”。员工从钉钉工作台报障、查看、补充和确认；工程师从通知进入移动待办，完成接收、备注、交接或解决；PC 适合大批量调度和复杂处理。两端读写同一数据库和事件时间线，不同步两份业务单。

钉钉聊天回复、群里说“已解决”或消息已读不直接改变工单。首期不依赖互动卡片回调，按钮可作为打开受鉴权 H5 的链接；语音按第 14 章只形成草稿。审批仍在已绑定的钉钉 OA 实例内进行，不把“接收工单”按钮复用为业务审批。系统最终状态以 ITSM 持久化结果为准，OA 结果必须经可信回调及权威查询对账后使用。

### 17.2 两端处理能力

| 使用人 | 平台入口 | 钉钉入口 | 结果落点 |
|---|---|---|---|
| 员工 | 本人工单及详情 | 工作台 H5、消息直达 | 补充、确认、重开、评价进入 ITSM；只看公开内容 |
| 工程师 | 我的队列和详情 | 我的待办 H5、接单/交接通知 | 同一动作 API，持久化负责人、记录、状态和审计 |
| 调度员或组长 | 组队列、人员及超时 | 待分派/升级 H5 | 授权派单、催办、特殊接管，记录理由 |
| 审批人 | 申请上下文的受限查看 | OA 审批 | 验证且绑定的结果回写 ITSM，不直接标交付成功 |
| 管理员 | 岗位与人员、角色、路由及集成管理 | 默认只接异常通知 | 特权修改在受控管理界面完成，必要时二次认证 |

H5 打开后先重新校验企业、本人及在职状态，再取最新工单与版本；链接只含不可猜测工单引用或短期上下文，不含 Token、手机号或权限证明。客户端不能指定真实操作者。失效会话重新免登，校验回跳地址白名单；授权码一次性消费、状态绑定、防 CSRF 和重放。移动网络中断时保留本地非敏感输入，未知提交结果先按幂等键查询，不盲目再次提交。

正式钉钉域名、HTTPS、应用可见范围、回调网络与移动端访问路径需现场确认。当前 `http://10.10.81.125:8080` 仅为受限内网开发入口，不能视为正式钉钉免登已满足要求；不为外出手机测试直接暴露内网服务器，采用经批准的 VPN 或受控接入方案。

### 17.3 通知对象和失败处理

| 事件 | 精准收件对象 | 员工可见内容 |
|---|---|---|
| 工单建立 | 员工；队列调度员或值班人员 | 编号、公开摘要、责任组及查看入口 |
| 个人候选或交接 | 指定接收人；原负责人；必要时组长 | 本人单公开进展，不含交接内部讨论 |
| 已受理或公开进展 | 员工及当前负责人 | 经脱敏公开摘要及最新进展 |
| 待补充或待确认 | 员工；负责人保留待办 | 要补充的问题或解决摘要、截止时间 |
| 接收超时或 SLA 风险 | 当前负责人、组长及规定升级人 | 仅按服务策略提供公开延迟说明 |
| 内部备注或外协明细 | 明确授权的当前处理人/协作者 | 不向员工、普通群或所有组成员推送 |

一期通知链路必须为“已确定的候选/实际负责人 employee_id → 目标企业有效 identity_links → 具体钉钉用户”。岗位多人只用于产生候选集合，不向所有任职人员发送包含完整工单内容的通知；组长/替补抄送按事件及当前权限另行确定。调度待办通知与个人处理通知分别建账，不把通知调度员视为已通知具体候选人。

每条发送记录以 `event_id + recipient_id + channel + template_version` 去重，发送前再次确认在职、任职/逐单授权和读取范围，并解析当前有效企业身份。没有有效映射时明确失败并进入受限工作台，通知有效兜底联系人，不能将模拟发送或厂商任务受理标为真实送达。“所有工程师都在一个群”不是责任落地方案；当前代码基础是否满足本节须按实际版本验证，不能因有通知适配器就认定岗位链路完成。工单提交成功只表示业务入库，不表示通知送达，送达也不表示本人已接收工单。

outbox 至少一次投递；维护发送中、厂商受理、已确认送达、失败重试、死信和已失权跳过等状态。厂商返回任务 ID 不等于已送达或已读；已有 receipt 状态按当前官方能力核实，不承诺不存在的已读回执。提交结果不明先查询厂商任务，不能盲目重发；平台无法保证绝对不重复展示，业务动作必须保持幂等。重试指数退避并有上限，死信进入受限工作台、审计重试和 P1 人工兜底，不回滚业务状态。

### 17.4 互动卡片的后续边界

仅在通知加 H5 闭环真实验收后，再评估可直接操作的互动卡片。是否支持相应卡片、授权及费用按企业实际官方能力 PoC；本版不捏造接口名称。即使卡片可点击，也须验证企业、事件签名、时间窗、事件 ID 和真实操作者，并通过同一领域动作服务鉴权；卡片 ID 或按钮可见不是授权。

卡片带业务版本上下文，旧卡片、重复点击、权限变化和交接完成后点击均重新读取当前状态。冲突返回刷新入口，不重复改变状态。卡片只显示脱敏必要字段，不能在群卡片中暴露权限明细、内部备注或安全证据。不能在卡片实现独立工单状态机，也不能用互动卡片替代 OA 高风险审批。

## 18 开发发布和交付提效

### 18.1 固定开发链路

本机仅存储和编辑代码、文档及操作 Git；不运行 ITSM 构建、应用测试、数据库、Redis 或 Docker。GitHub CI 在隔离环境构建和测试；`10.10.81.125` 运行开发验证环境，保持现有访问网段及端口边界。现有 ELK、监控和本地大模型继续在其既有服务器，不为开发方便复制到本机。

2026-11-16 用户确认一期、二期、三期均采用集中交付：当期范围冻结 → 阶段集成分支集中开发 → 持续 GitHub CI → 单个集成 PR 审查及 main 合并 → main 固定制品 → 开发服务器集中受控部署 → 现场联调和业务验收。每期分别交付，不是三期开发完才部署。

切片用于组织开发、小提交、审查和测试，不再要求逐切片创建 PR、合并或部署；在有意义的模块检查点推送并运行 CI，最终 SHA 必须通过完整门禁。开发期保持当前服务器可用版本，真实接口权限、身份映射、模板和回调网络等前置核对提前开展。阶段验收通过后推进下一期正式开发；范围调整须显式确认，未验收外部能力不能以模拟结果结清。

默认每期一次计划内集中交付；验收缺陷集中修复回归后可以补发，安全止损和服务恢复可走受控紧急通道，不承诺一次部署后零补丁。先读取当前基线、部署证据和待办，再做与本轮任务有关的检查，避免每轮重做全环境盘点。监控与配置项关联第二期、完整 SEC 第三期以及语音独立试点的边界保持不变。

### 18.2 非交互发布前置条件

当前既有发布演练不等于已建立内网自动部署。新增专用最小权限部署身份，使用受控 SSH 密钥或等价短期身份；禁止聊天传密码、保存个人 GitHub 登录凭据或配置不受限免密 sudo。以固定发布入口校验 SHA、制品清单及允许参数，拒绝任意 shell、任意 Compose 参数和任意路径执行。

首次配置需要一次受控管理员操作，此后普通发布应不再反复要求用户输入密码。部署身份仅访问 ITSM 发布目录、受限拉取凭据及发布入口；对 Docker 权限按高权限能力管理，不能把加入 docker 组视为普通低权限。密钥定期轮换和可撤销，密钥材料不进入仓库或文档。

内部网络无法从 GitHub 直接连接时，采用服务器主动拉取已通过门禁的 main 制品，或专用可信发布节点；不在承载其他服务的开发服务器上执行任意 PR 的自托管 runner。自动部署上线前明确项目路径、环境配置、备份目的地、磁盘容量、维护窗口、回退责任人及访问控制；不新增宽泛公网入口。

### 18.3 流水线和发布门禁

1. 快速反馈阶段先做格式、类型、单元和迁移不可变检查；完整合并门禁继续包含安全扫描、隔离集成、浏览器和发布演练，不能靠跳过失败测试提速。
2. 按实际耗时配置依赖及构建缓存；集成测试先隔离数据库与测试数据再并发。区分基础设施暂态失败和业务断言失败；时序测试对持久化状态做有界等待，不降低业务断言或无限重试。
3. 功能分支同组运行取消过时任务；main 正在执行的发布不能自动中断，并发发布必须串行和加锁。合并前验证最新 SHA，旧提交的成功不能代替当前提交。
4. 只部署通过完整门禁的 main 制品，核对提交 SHA、制品哈希清单和不可变镜像摘要；发布锁、备份、隔离恢复检查、迁移、健康及业务冒烟均保留。
5. 发布后核对各容器实际镜像与服务器实际运行版本，再执行文字建单、到人、处理、确认的业务验收；页面可打开或镜像已发布均不等于部署验收完成。
6. 迁移采用可向前兼容策略并声明回退边界，不能承诺任意数据库变更自动回退。新增角色约束后，旧版本若可绕过权限，不可直接作为安全回退应用。

### 18.4 每次交付证据和效率指标

每次交付固定报告六项：新增可操作能力、源码 SHA、完整 CI 运行号及最终结果、服务器实际运行 SHA、可复现验收步骤及是否模拟、未完成项与下一动作。分别记录“设计已写、代码候选、CI 通过、已部署、业务验收、真实外部联调”，不压缩成一个完成勾选。

先采集五次完整交付的基线：提交到 CI、CI 到部署、部署到验收耗时；同时统计重跑次数、人工认证次数和验收通过的业务切片数。随后选择最耗时环节优化，不承诺未经测量的加速倍数。交付效率优化与第 11.2 节分期并行，不将工程 CI/CD 推迟到第三期业务发布管理。
