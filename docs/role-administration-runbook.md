# 角色授权与派单运维说明

本说明对应 V1.2 的 R1 和部分 R2，服务于 BASE-01、P1-02、P1-03、P1-04。当前边界于 2026-11-23 按管理员直接配置候选更新。
这是操作说明，不是 CI、部署或业务验收证明；一期完整核对见 `phase1-core-acceptance.md`，可执行用例见 `phase1-core-uat-cases.md`。

## 当前边界

- 固定角色 `PLATFORM_ADMIN`、`DISPATCHER`、`GROUP_LEAD` 由有效平台管理员直接配置、撤销并留审计；旧提案与独立复核接口保留。
- 工程师身份仍由有效员工、支持组成员关系和具体工单归属共同确定，不另建登录账号。
- 普通组成员不能给未接单工单派人或纠正分类；调度员、组长只能在有效授权组内操作。
- 已受理工单的原负责人可发起实名交接；目标工程师接收前，原组和原人继续负责。未接单派人沿用候选交接，不伪造本人已受理。
- 平台管理权不授予全量工单读取权，也不授予 OA 业务审批权。P1 确认仍使用独立的 `priority_reviewers` 任命，不自动从组长角色继承。
- 支持组、成员、服务组织及任职可由平台管理员直接保存，保留停用/恢复及依赖检查；组长提案仍须独立复核。人员来自可信目录，详见 `admin-configuration-guide.md`。
- 已有主管发起交接、本人确认接收及逐单限期继续处理授权。本批另补齐实际 `FORCE_TAKEOVER`、厂区作用域和组长受限任职维护，操作边界见 `p1-operations-scope.md`；紧急接管不伪造首响、不重置 SLA，也不取消既有等待。完整排班、服务经理和审计员角色仍未完成；候选代码能力须经 CI、发布及真实联调分别验收。
- 真实钉钉免登、通知送达、OA 和可信离职源仍须单独联调及现场验收；不能为了角色测试开放未满足条件的入口。

## 一次性管理员初始化

仅在已批准的开发机发布目录、迁移成功且未开启开发种子数据时执行。
先确认两名不同的真实在职员工已存在于 `employees`，并核对稳定员工 ID 和身份映射；本命令不创建员工、不修改登录配置。

```sh
sudo -H docker compose --project-name itsm-dev --env-file /实际受保护的环境配置文件 -f infra/compose/compose.yaml exec -T \
  -e ITSM_ROLE_BOOTSTRAP_CONFIRM=INITIAL_TWO_ADMINS api \
  node apps/api/dist/bootstrap-role-admins.js \
  --first '已核对的第一位员工ID' --second '已核对的第二位员工ID' \
  --reason '已批准的初始化记录编号'
```

环境文件路径从当前发布配置取得，不复制示例占位符执行，不在命令行或文档放密钥。
脚本在事务内取得排他授权锁、复查两人有效状态，创建有效期 365 天的两项平台管理授权并写两类审计。
只要数据库存在任何平台管理员授权历史，就拒绝再次引导，包括授权已撤销或到期的情况。
真实人员不能用演示管理员替代；开发种子账号只允许隔离开发/CI 环境。

## 演示管理员交接为真实人员

数据库已存在演示管理员历史时，不能重复初始化或将演示员工改名。迁移 `042_admin_handoff.sql` 提供一次性离线交接路径；它不开放 HTTP 接口，不冒用两名真实员工的审批身份。

1. 从已验证的主分支发布制品部署新版本，保留变更前数据库、附件及配置备份。生产认证配置必须关闭开发登录；真实通知在完成试点验收前保持关闭。
2. 配置企业 ID、明确的部门根及试点用户 ID 白名单，关闭目录缺失自动停用。先在 worker 运行 `node apps/worker/dist/directory-once.js` 预览；核对人名与稳定用户 ID 后使用同一命令加 `--apply` 同步。凭据只从受保护的运行环境取得。
3. 准备不含密钥的 JSON 选择文件：`requestId`、`corpId`、`roots`、`pilotUserIds`、两名 `admins[{userId,name}]`、现有两项演示平台授权的 `previousBindingIds`、`executionPrincipal`、真实授权来源 `authorityRef`、`reason`、`configurationSha256`、`backupRef`、`validUntil`。有效期须大于一天且不超过 365 天。
4. 在 api 容器向标准输入传入上述 JSON，并设置 `ITSM_ADMIN_HANDOFF_CONFIRM=TRANSFER_DEMO_ADMINS`，运行 `node apps/api/dist/handoff-role-admins.js`。默认只预览，不修改权限。核对预览后加 `--apply` 执行；该模式还要求 `NODE_ENV=production` 和 `ENABLE_DEV_AUTH=false`。
5. 工具校验 15 分钟内成功完成的同企业、同部门根及同试点白名单同步，核对有效员工、目录与身份映射、人名及两项原始 BOOTSTRAP 演示授权。演示账号若关联真实身份则拒绝执行。
6. 同一事务内建立两项真实管理员授权，撤销两名演示管理员全部有效或待审授权、停用演示员工并清除会话。旧员工、工单及授权审计历史保留。任何失败完整回滚；成功后拒绝重放。
7. 核查恰好两名真实管理员有效，其他试点员工无平台管理权限。授权审计显示实际维护执行主体及授权依据，不能显示伪造的人工批准。随后由本人在钉钉登录，验收角色维护及旧演示入口关闭。

交接后的人员增减与续期使用下述后台角色授权流程，不能重复执行交接命令。备份恢复须同时考虑配置和数据库，并保留本次交接证据，不能通过删交接记录再次执行。

## 日常授权

1. 管理员从“角色授权 → 新增角色人员”选择现有员工、固定角色、支持组和有效期，填写原因并声明内容不含敏感证据。
2. 点击“保存并生效”，当前有效平台管理员可直接配置本人或他人；组范围角色会自动补齐所选员工的支持组成员资格。
3. 系统记录 `ADMIN_DIRECT`、真实执行者、原因与前后状态。直接配置不标记为独立复核；待复核历史记录仍按旧规则处理。
4. 保存时再次校验在职状态、目标组及有效期。组长只能提议本组角色，不能提议平台管理员或给自己授权，仍须由不同于提案人及被授权人的有效管理员复核。
5. 撤销后服务器按数据库最新授权拒绝后续操作，已有会话和旧幂等键不能保留派单权。操作失败后刷新最新版本，不直接改库补状态。
6. 通过统一“操作日志 → 角色授权”查看提案、复核、撤销和原因，页面的“查看相关日志”可带入对象。权限变更不修改历史工单责任或 SLA。

普通撤销一名有效平台管理员时，必须保留至少两名其他有效管理员，否则返回 `ROLE_ADMIN_CONTINUITY_REQUIRED`。
建议建立三名独立在职管理员，以便权限交接和连续性维护；现有有效管理员可直接为第三人配置角色。管理员直接保存不取消上述撤销连续性约束。
这不是三人可共用的账号，也不是要求任何人拥有业务数据全量权限。

## 到期与异常处置

- 有效期按每次请求实时判断；`ACTIVE` 状态记录仍可能已经到期或因员工/成员关系无效而失权。
- 当前唯一约束保留未结清的 `PENDING`/`ACTIVE` 记录。到期续授前，由有效管理员先撤销旧记录，再直接保存新授权；不能覆盖历史记录。有效管理员可维护本人，但撤销平台管理员仍受连续性条件约束。
- 有效管理员不足或全部到期时，不能重复运行引导脚本自恢复。当前没有线上自助恢复通道，须升级给系统负责人制定独立审批、限时执行、可回退且留审计的恢复变更。
- 人员紧急停用不能被普通管理员连续性规则阻止。已有可信目录同步、停用撤会话及工单责任恢复代码；实际离职数据源、同步时效和企业身份仍须联调。紧急处置按既有身份系统流程执行，并核查在办单及待交接恢复，不直接删除历史员工。
- 撤销角色只撤销该角色能力，不等于员工离职，也不会自动移除工程师组成员关系或删除历史工单。

## 派单配置

- 只有当前有效的平台管理员能查看和提交“派单配置”。配置变更先进入待复核状态，另一个当前有效的平台管理员批准后才生效；提交人不能自行批准。拒绝不修改现行配置。
- 接单时限按支持组和 P1-P4 优先级独立配置，包含工作日历、起止时间和分钟数。停用是带审批的变更，不删除历史版本，也不改变已经创建的候选派单和工单 SLA。
- 备用组按支持组配置，禁止自指和间接循环。修改基于界面显示的版本；出现版本冲突时先刷新核对现值，不应直接编辑数据库绕过复核。
- 每次提交、批准或拒绝均保留申请人、复核人、原因和前后快照。钉钉通知不代替平台内的审批与审计。
- `db/seeds/dev.sql` 内的演示管理员、接单时限仅供隔离开发/CI 使用；正式环境必须先完成真实管理员引导、配置申请与独立复核，不能把演示时限当作业务承诺。

## 验证与发布要求

`tests/integration/roles.mjs` 只允许 GitHub 隔离 CI：覆盖作用域、独立复核、真实 cookie 会话撤权、版本竞争、派单交接、SLA 契约和审计；引导验证使用单独生成的临时数据库，不清空应用授权表。
`tests/e2e/roles.spec.ts` 覆盖桌面直接保存与手机撤销、审计及横向溢出检查。
`tests/integration/routing-config.mjs` 只在一次性 GitHub CI 数据库运行，检查待审不生效、独立批准、版本冲突、停用、防环和审计。开发机需在发布后另行核对业务操作和回执。
CI 全绿、主分支制品生成、开发机部署、版本对应和业务验收需要分别留下证据，任何一项不能由本说明替代。

`tests/integration/admin-handoff.mjs` 在 GitHub 临时独立数据库覆盖真实目录映射、试点过滤、预览无写入、旧授权及身份校验、过期同步拒绝、事务回滚、演示会话撤销、既有角色授权与审计页面服务、保留历史、重放拒绝，以及普通授权的独立复核约束。

`tests/integration/admin-configuration.mjs` 在一次性独立数据库覆盖管理员直接保存、本人配置、自动补齐成员、目录与路由原子发布、旧复核约束、越权拒绝、幂等及失败回滚。本次不改变“派单配置”、业务审批、交付及 P1 独立确认流程。
