# P1-07 受控人工交付与回收工作台（代码候选）

当前候选包含工程师“交付与回收”工作台、准备与首次交付的异步受理入口、独立复核及实际撤权登记 API，并增加审批结果与工单状态联动、交付完成及员工确认门槛。所有交付均由人员在目标系统实际执行，平台不自动开通下游权限。REQ 公开提交的服务端阻断继续有效；真实 OA 接口和业务策略未联调前，不将本能力记为上线或验收。

## 规则

- 审批账本为 `APPROVED` 且有当前验证凭据仍不等于授权。准备任务和确认人工交付前，都重新向 OA 读取权威实例，并在同一数据库事务中核对实例、企业、模板、申请人、审批人、不可变申请内容、在职身份、主管映射、工单状态和期限。回调先到会清除凭据，阻断旧查询结果。
- 准备及首次交付人员必须在职、属于当前启用责任组，并满足原工单岗位快照对应的当前有效任职，不得是申请人或审批人；组长身份不绕过首次交付的任职要求。任职停用、到期、尚未生效，或岗位/责任域停用，立即拒绝这两类动作。交付任务按审批和工单各限一条，留存受理人及 `READY` 状态。实际执行后，凭外部变更单编号记录交付时间、不可变有效期和执行人；数据库不保存密钥或下游凭据。重复交付被拒绝。
- 交付后由另一名在职责任组成员复核下游实际授权并留存独立外部记录编号；复核人不能是执行人、申请人或审批人，并需满足原工单岗位快照对应的当前有效任职。复核只补充不可变时间/身份及事件，不改变交付状态，不能代替真实下游核查。工作台提供待复核队列，定向提醒和逾期组长升级的候选实现见下节。
- 取消、撤销、拒绝、人员失效、身份变更、审批失去验证或到期时，未执行任务转 `BLOCKED`；已交付任务转 `REVOKE_DUE`，等待人员在下游撤权并凭外部变更单编号登记 `REVOKED`。此处仅产生回收义务，不谎称已经自动撤权。
- OA `expires_at` 是首次交付截止时间；已审批且已交付的访问期限由 `access_expires_at` 单独控制。回调让批准凭据失效时，现有交付需要进入待回收。审批通过后工单进入 `IN_PROGRESS`，但不自动创建交付任务、指定个人负责人或记作人工响应；交付及复核后仍须工程师显式提交完成，再由员工确认或满足统一条件后超时关闭。
- 配置发布与交付事务共用授权读写锁；交付等待锁后重读已生效任职，并在人员/工单锁检查后按实际数据库时钟复核期限，不能凭事务开始时尚未过期继续交付。交付时间及访问到期时间按锁等待后的实际时间登记。待交付人员失去资格时，维护任务将 `READY` 转为 `BLOCKED` 并记 `DELIVERY_OPERATOR_UNAVAILABLE`；重新任职不自动恢复已阻塞任务。已交付任务不因原工程师离岗单独触发回收，仍按申请人、审批及访问期限判断。

## 工程师工作台与接口候选

后台按当前有效支持组范围显示待复核、待回收和全部任务，支持责任组筛选、每页 20 项及详情历史。详情最多显示最近 100 条事件并明确提示截断；完整不可变历史仍留存在数据库。普通申请人只能读取自己的进度投影，不可读取执行记录编号、内部审批快照、OA 实例绑定或错误内容。

| 接口 | 行为 |
| --- | --- |
| `GET /api/v1/fulfillments?queue=UNREVIEWED\|REVOKE_DUE\|ALL&group=...&page=1` | 当前支持组范围内队列、计数和分页 |
| `GET /api/v1/fulfillments/{id}` | 任务事实、当前操作资格及最近历史；范围外返回 404 |
| `POST /api/v1/fulfillments/{id}/review` | 独立复核实际交付 |
| `POST /api/v1/fulfillments/{id}/revoke` | 人工实际撤权后登记结果，不代替下游撤权 |
| `GET /api/v1/fulfillments/intake?group=...&page=1` | 当前责任组内待准备、已准备及本人近期操作回执，每页 20 项 |
| `POST /api/v1/fulfillments/intake/{approvalId}/prepare` | 202 受理准备意图，不能视为任务已经领取成功 |
| `POST /api/v1/fulfillments/intake/{approvalId}/deliver` | 202 受理实际交付登记意图，不能视为后台已经核验通过 |
| `GET /api/v1/fulfillments/delivery-failures?group=...&page=1&resolved=false` | 当前责任组内持久待核查队列；`resolved=true` 查询已核查历史 |
| `POST /api/v1/fulfillments/delivery-failures/{commandId}/resolve` | 另一名当前合格人员记录实际核查结果，原失败回执不变 |

写操作必须提供 UUID `Idempotency-Key` 和完整正文 `{expectedVersion, reference, contentClass: "GENERAL"}`，外部编号只接受受限字符，不能保存凭据。重复相同命令返回原始不可变回执；同 key 改内容或旧业务版本返回 409。即使是成功命令重试，也先重新检查账号、当前成员和任职资格，已撤权者不能靠重试读取回执或继续操作。后台轮询只更新时间戳，不推进业务版本；业务状态、交付、复核和回收事实变更才推进版本。

复核及回收在 API 和 worker 内调用同一数据库动作，共用授权锁及“审批 → 交付任务 → 工单”加锁顺序。回收允许当前有效任职人员或当前责任组有效组长兜底，防止原操作员离岗后无人能登记实际撤权；组长兜底不豁免独立复核要求。已存在的历史空路由快照仍采用当前有效组成员规则，不补造任职快照。迁移 `022_request_delivery_eligibility.sql` 为准备及首次交付统一当前任职校验；真实 OA 准入及操作入口须另行验收后开放。

前端撤权登记要求勾选“已在目标系统实际完成撤权”，成功后显示回收登记事实与记录编号，不能以“审批取消”冒充撤权成功。错误、加载、空队列和刷新入口均保留；页面按钮可见性不是后端授权的替代品。

## 准备与首次交付异步入口候选

`ENABLE_MANUAL_REQUEST_DELIVERY` 在 API 和 worker 默认均为 false。API 开关只开放受理，不代表 worker 或 OA 已启用；worker 还必须有由 `ENABLE_LIVE_OA_APPROVAL` 及真实企业配置建立的 OA 提供方。正式启用需同时核验两个进程的配置、实际 OA 查询和处理回执；不能只开 API 让操作长期停在排队状态。CI 只临时开启一次性 API，并使用测试脚本注入模拟提供方，不给运行中的 worker 开启真实 OA 或通知。

准备正文严格为 `{expectedVersion:0,contentClass:"GENERAL"}`；首次交付正文严格为 `{expectedVersion,reference,actualDeliveryConfirmed:true,contentClass:"GENERAL"}`。两者均要求 UUID 幂等键。只有实际交付人能登记该 READY 任务，申请人、审批人、失效任职和范围外人员均被拒绝。外部记录编号受普通内容保护，不接收密码、密钥或任意附件。

迁移 `024_request_delivery_commands.sql` 保存不可变意图和一次性终态。每个审批至多一条 PENDING 命令，命令有效期为 10 分钟；HTTP 返回 202 和 PENDING 回执，不持有外部 OA 查询事务。worker 读取 OA 后，在授权锁、命令行锁、审批/任务/工单锁及当前资格核验下提交任务、事件和 SUCCEEDED 回执；任何失败全部回滚业务事实，另将回执设为 REJECTED。等待其他锁导致超时也不能登记成功。重复 worker 可重复只读核验，但不能重复创建任务或交付事件；相互竞争的失败核验可能使该命令被拒绝，须人工核对后用新键重试，不会自动执行下游权限动作。

回执仅向仍有当前责任组范围的操作人展示；包含固定原因码，不保存远端异常原文。相同键和正文重放返回原回执，已撤销账号、成员或任职不能靠旧键继续操作；同键不同内容返回冲突。终态不能更改或删除，也不自动重试 REJECTED。用户检查失败原因后可明确提交新命令。

“交付与回收”中进入“准备与首次交付”，显示尚未准备、READY、BLOCKED 及本人一天内完成的操作。页面分开显示“等待后台核验”和“核验通过，操作已记录”，挂起时每 3 秒刷新当前列表，并保留手动刷新。实际交付必须勾选事实确认和普通内容边界。该入口不改变现有工单状态、不授予下游权限，也不解决交付后工单状态联动；正式 REQ 仍关闭。

## 定向提醒与逾期升级候选

迁移 `023_fulfillment_attention.sql` 为每个任务、当前责任组和提醒类型保存不可变信号，事件、审计和通知 outbox 在同一事务提交。重复轮询及并发 worker 不重复创建同类信号，不推进交付或工单业务版本，不改工单状态、负责人或 SLA。每轮最多处理 100 个审批，优先最早待办；沿用约 30 秒一次的维护周期，不承诺精确到秒的送达。

| 提醒 | 条件和接收范围 |
| --- | --- |
| 待独立复核 | 已交付、访问尚未到期且未复核；仅当前具备复核资格的任职人员，排除执行人、申请人和审批人 |
| 待实际回收 | 已进入 `REVOKE_DUE` 或已交付访问到期，关闭工单也不免除回收义务；当前具备回收资格的任职人员及有效组长兜底 |
| 复核逾期 | 从实际交付时间计算提醒升级期限，仍有复核义务时通知当前有效组长 |
| 回收逾期 | 从访问到期或首次提前回收义务中的较早时间计算期限，仍未回收时通知当前有效组长 |

`FULFILLMENT_REVIEW_REMINDER_MINUTES` 默认 1440 分钟，`FULFILLMENT_REVOKE_REMINDER_MINUTES` 默认 60 分钟，均只接受 1 至 10080 的整数。它们是可调整的技术提醒阈值，不是已经批准的公司 SLA；业务应在正式启用前确认。首次信号持久化具体升级时间，修改环境变量不会重新计时或覆盖既有信号。逾期信号最早在创建首次提醒后的下一轮维护生成。无有效组长不伪造升级接收人，也不扩大到全员或申请人。

通知展开及每次发送前共用当前资格查询，重新核对任务义务、责任组、账号、成员、有效任职或组长角色；已复核、已回收、失去任职或更换责任组的旧提醒不再发送。新责任组可以生成自己的信号；回到曾经提醒过的组不重发该组同类信号。提醒只包含工单编号、待办类别和 HTTPS 工作台链接 `#/fulfillments`，不携带审批正文、证据编号或密钥。普通员工通过该链接不能进入工程师工作台，API 仍独立鉴权。

迁移 `027_fulfillment_notification_audience.sql` 增加接收人重查时间和当前有效信号视图。worker 对已展开、仍存在复核或回收义务的信号重查当前接收人，每轮最多 20 个，单信号至少间隔 60 秒，优先从未重查和最早重查的记录。空岗后新增的合格人员可以补入原信号；已完成复核、已回收、已失效或旧责任组信号不补发。已关闭工单的实际回收义务仍可补入新任操作人员。展开和重查共用授权锁与当前资格查询，发送前仍重新核验资格。

补入复用原事件、审计和 outbox，不新增业务信号、不推进工单或交付版本、不改首次展开时间；同一信号和人员仅保留一条投递。已有 `PENDING`、`SENDING`、`DELIVERED`、`SKIPPED`、`DEAD` 和 `SIMULATED` 投递均不重置，重新获得任职也不自动重放已跳过或失败的投递。每批新增投递与重查时间在同一事务提交，失败全部回滚，并发 worker 跳过已锁记录。旧数据的空重查时间无需伪造历史接收人，可在义务仍有效时逐批补查。

沿用现有通知开关、重试和死信处理，不因增加扫描就启用真实钉钉发送。人员恢复补查不是周期性重复催办，也不能保证无人状态立即通知到人。工程师和主管仍须检查工作台队列、消息失败及人员覆盖；当前未新增无人接收专用告警。新增隔离 PostgreSQL 测试覆盖真实任职新增、原事件复用、状态不复活、已完成/旧责任组抑制、关闭后回收、批量公平性、失败原子回滚及并发去重，须以本候选最终 SHA 的实际 CI 结果为准；真实送达及运营兜底需现场验收。

## 验证范围

新增单元、隔离数据库集成和桌面/手机浏览器用例，覆盖范围外拒绝、执行人/申请人/审批人不能复核、任职撤销即时生效、组长兜底回收、同 key 并发一次生效、不同命令版本竞争、重复证据拒绝、不可变回执/事件、业务版本与维护时间分离、分页与历史截断，以及真实 API 驱动的复核和回收登记。测试仅在 GitHub Actions 隔离环境运行，以最终同一 SHA 的完整结果及截图检查为准；此文档本身不是通过或部署证明。

准备及首次交付的隔离集成另覆盖有效任职与职责分离、组长不能绕过任职、岗位/责任域/人员失效、OA 读取期间撤销任职、等待发布锁时撤销任职、锁等待后的期限及交付时间、待交付任务阻塞与已交付权限不因原工程师离岗误回收。OA 使用隔离测试提供方，不代表真实钉钉联调。

提醒候选增加解析边界及安全文案单元测试、数据库原子性/并发去重/持久化期限/当前接收资格/关闭工单回收/逾期组长/完成后抑制集成测试，以及桌面和手机的工作台深链及普通员工拒绝用例。新增测试在相同提交的完整 CI 验证前不能标记已通过。

异步入口增加默认关闭、HTTP 202 不代表业务成功、正文与事实确认、本人受限回执、丢失响应复用同一键、双 worker 同一命令只落一次事实、OA 撤回/回调失效、排队后任职撤销、过期、锁等待后超时回滚、终态不可变、成功回执写入失败时事务回滚、显式新命令重试、分页及桌面/手机截图。仅为模拟提供方环境下的接口及工作台验证，不证明真实 OA 已接通。

失败回执按操作区分：准备失败可说明未准备；工程师已确认实际执行的交付登记失败，只能说明登记未通过、实际授权需人工核查，不能声称目标系统未执行或已自动回收。回执区域保留可访问的命名区域，桌面与手机浏览器覆盖该失败状态。独立核查队列代码候选见下节，真实下游事实仍须由人员核查。

顶部操作提示以本次提交返回的回执 ID 绑定当前任务，随后跟随列表轮询或手动刷新取得的同一回执状态更新，不再固定保留“等待后台核验”。切换任务时清除本次提示，历史回执仍显示于详情；不同回执不得作为本次提交的成功凭据。浏览器回归覆盖准备和交付登记失败的自动轮询、准备与交付成功的手动刷新，以及重选任务后不残留顶部提示。上述界面修正不替代失败交付补偿队列或真实下游核查。

## 交付登记失败独立核查候选

迁移 `025_delivery_failure_resolution.sql` 增加不可变核查记录。失败的 `DELIVER` 回执持续留在“登记失败核查”队列，不受准备入口最近一天的回执窗口限制；工单关闭、审批失效或任务阻断也不会消除核查义务。准备失败不产生可能已授权的核查义务。队列按当前责任组隔离，每页 20 项，可切换待核查和已核查；不返回 OA 快照、提供方错误或下游凭据。

同一申请存在未核清的失败交付登记时，API、新意图及 worker 直接调用均禁止再次准备或登记交付。相同原命令重试仍返回原失败回执，不伪造成功。核查只允许 `NOT_GRANTED`（在目标系统核实未产生授权）或 `REVOKED`（在目标系统完成并核实实际撤权）；如果仍需保留实际授权，先按公司受控处置流程核清并完成必要撤权，不能把不确定授权直接追认为成功。此候选不提供保留授权、补登成功或自动下游撤权。

核查人须在职且为当前责任组成员，并具有原岗位快照的当前有效任职或当前有效组长角色；不能是原失败登记人、申请人或 OA 审批人。组长仅可兜底独立核查，不因此获得首次交付权限。提交完整正文 `{outcome, reference, actualVerificationConfirmed: true, contentClass: "GENERAL"}` 和 UUID 幂等键，提供不同于原登记及已有交付/核查记录的外部核查编号。存在成功交付而尚未登记实际回收的任务时，先走原回收链，不能借核查绕过已登记授权的撤权义务。

核查事务共用授权锁及“审批 → 任务 → 工单 → 失败命令”锁顺序，重新核对资格，按人和幂等键去重。独立核查记录、工单事件、审计和通知出站记录原子写入；并发不同核查最多一笔生效。核查不修改原失败回执、任务交付事实、工单状态/负责人/版本或 SLA。核清后仍需一个新的显式交付意图，并重新满足有效任职、审批验证及执行窗口，不能自动重放旧命令。
