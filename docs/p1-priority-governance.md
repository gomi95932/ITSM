# 工单优先级治理设计与实现

版本：V1.0；日期：2026-11-21；状态：代码候选，验证结果见文末。

本补充遵循 V1.1 分期和 `implementation-baseline.md`。一期补充分级、人工核实、P1 独立确认及可配置规则；监控和配置项关联仍在二期，完整安全事件流程仍在三期。真实钉钉接入暂缓，本次不变更应用权限和服务器凭据。

## 1. 分类原则与管理定义

工单类型、服务目录和优先级分别维护。INC 表示故障事件，REQ 表示申请，GEN 表示待分流的普通事项；服务目录界定服务和责任岗位；P1-P4 表示处理优先顺序。高优先级不会绕过 REQ 审批、自动获得系统权限或派给未经授权的人员。

本轮保持已有 P1-P4，暂不增加 P0，避免历史数据和报表出现两套等级。这里的 P1 是企业内部最高处理优先级，不是国家网络安全事件分级。

| 优先级 | 管理含义 | 电子制造场景示例 | 处置原则 |
| --- | --- | --- | --- |
| P1 重大 | 核心生产/发运或较大范围业务严重受阻 | 核心 WMS 中断影响生产供料；全公司网络不可用 | 立即响应，同时独立主管确认 |
| P2 高 | 局部业务明显受阻，或个人工作完全中断 | 局部业务异常；单人电脑无法开机且无替代机 | 优先处理，必要时升级 |
| P3 一般 | 有影响但工作仍可继续 | 单人操作间歇异常，有替代操作 | 按服务时限处理 |
| P4 低 | 影响轻微、咨询或可计划事项 | 设置咨询和优化事项 | 计划处理 |

示例用于培训，实际结果由批准的矩阵和关键服务清单决定。员工职位高低、描述措辞强烈、申请人要求加急，不单独构成最高优先级依据。安全证据继续走既有受控入口，不进入普通工单或普通 AI 分析。

## 2. 自动判定与人工核实

流程：员工简述/语音草稿 → AI 提取有原文依据的影响范围和紧急程度 → 员工采纳或自行填写 → 服务端计算初始优先级 → 路由到责任岗位/人员 → 服务台或工程师核实调级 → P1 独立确认。

### 2.1 默认矩阵

| 影响范围 | 高：工作中断且暂无替代方式 | 中：工作明显受影响 | 低：可继续工作或可计划 |
| --- | --- | --- | --- |
| 全公司/核心生产 | P1 | P1 | P2 |
| 部门/多人 | P1 | P2 | P3 |
| 单人 | P2 | P3 | P4 |

默认值兼容已有行为，是试行基线。管理员可调整；系统拒绝随影响或紧急程度增加反而降低优先级的矛盾配置。

关键服务覆盖：只有清单内服务且紧急程度为 HIGH，才覆盖矩阵进入 P1 候选。建议将核心生产 WMS 故障单独建服务目录，不将范围过宽的“全部业务系统”列为关键服务。初始清单为空，业务确认后配置。

### 2.2 AI 边界

- 既有文字/语音智能草稿解释器增加可选 `priorityEvidence`，包含 `impact`、`urgency` 和各自原文摘录。
- 信息不足输出 null。服务端校验结构、枚举和摘录确实存在；模型不能返回可执行指令、直接指定等级、确认 P1 或执行审批。
- 页面展示依据，员工明确采纳后仍可修改；修改描述后旧建议失效。
- 模型不可用或输出不合法时保留人工填写。原文摘录校验不能保证语义正确，仍须人工核实。
- 创建时保留草稿证据、人工事实输入、初始结果和规则版本。普通手工录入同样按矩阵计算。

## 3. 权限与职责

| 人员 | 可执行操作 | 边界 |
| --- | --- | --- |
| 员工/代报人 | 填写或采纳事实、补充影响说明 | 不能经接口直接指定/调整等级 |
| 当前符合岗位处理资格的负责人 | 建议调级、直接升级 | 不可自行降级，同组成员身份不自动赋权 |
| 有效服务台调度员/组负责人 | 核实事实，调整非 P1 工单 | 当前责任范围内，必须填写原因 |
| 当前组授权 P1 主管 | 确认 P1 或独立调整；核实普通分级 | 不可确认本人提交、代报或刚升级的 P1 |
| 平台管理员 | 提出矩阵、时限、关键服务和提醒配置 | 另一有效管理员独立批准后生效 |

P1 候选不等待确认即可领取、响应。缺少独立确认人时页面提示并保留提醒，由管理者补齐任命。P1 候选阶段的调级须走独立确认；已确认 P1 的降级也要求独立授权主管。

终结或待员工确认的工单不可普通调级。建议记录事实及意见，不改变等级或 SLA。变更以乐观版本和幂等键控制；审计和通知 outbox 在同一事务提交；权限失效后不可继续操作。

## 4. SLA 与提醒

| 等级 | 首次响应 | 解决/交付 | 计时方式 |
| --- | --- | --- | --- |
| P1 | 15 分钟 | 240 分钟 | 连续时间 |
| P2 | 30 分钟 | 480 分钟 | 服务日历内时间 |
| P3 | 240 分钟 | 1080 分钟 | 服务日历内时间 |
| P4 | 540 分钟 | 2700 分钟 | 服务日历内时间 |

默认日历为上海时区工作日 09:00-18:00。节假日、值班能力和时限需业务确认，P1 连续计时不代表已建立 7×24 值守。REQ 审批、交付和等待规则保留，高优先级不可越过审批。

P1 主管确认默认 5 分钟后产生一次持久提醒。这不是首次响应，也不是电话/短信/轮询升级链。钉钉关闭或模拟发送如实展示，实际服务商确认后才算真实发送。

1. 创建时冻结初始等级、规则版本、目标和日历，旧单不随配置修改重算。
2. 降级保留原时钟、目标、超时记录，不能消除历史违约。
3. 升级追加从升级时刻开始的更严格时限，原时钟并行保留；任一超时即算超时。已首次响应的无需重复首次响应。
4. 既有等待用户暂停规则继续适用；追加时限仅扣除自身区间内的有效暂停，P1 用连续时间口径。
5. 重开新周期按重开时规则取新目标，历史周期保留。派单等待受各条 SLA 剩余预算约束。
6. 再升入 P1 生成新候选代次，重新提醒和确认；旧代次待发提醒不对新代次重复发送。

## 5. 配置、数据与接口

后台“分级与时限”维护矩阵、四级时限、关键服务及 P1 提醒分钟数。独立审批记录原因、时间、版本、审批状态；过期版本不可覆盖。新配置影响新建工单和后续升级目标，原始时限保持。

数据库迁移 `037_priority_governance.sql`：

- `priority_policy_versions`、`priority_policy_proposals` 保存版本与审批。
- 工单增加 `initial_priority`、`priority_policy_snapshot`、`priority_changed_by`、`priority_review_generation`。
- `priority_review_signals` 按工单、类型、代次去重。
- `sla_cycles.priority_obligations` 保存升级时限，`pause_history` 保存暂停区间。
- 历史工单按最早已有确认事件恢复初始等级，缺记录则用当前等级，不能还原从未记录的历史事实。

| 接口 | 用途 |
| --- | --- |
| `GET /api/v1/admin/priority-policy` | 当前规则及最近审批 |
| `POST /api/v1/admin/priority-policy` | 提出配置，含 UUID、基线版本、原因 |
| `POST /api/v1/admin/priority-policy/:id/review` | 独立批准/拒绝 |
| `POST /api/v1/tickets/:id/priority` | APPLY 调级或 SUGGEST 建议，含事实、目标、原因、版本、幂等键 |
| `POST /api/v1/tickets/:id/priority-review` | P1 候选独立确认或调整 |

详情展示初始/当前等级、创建规则版本、确认状态、调级人和原因；报表增加初始等级、调级次数、追加 SLA 结果。

## 6. 实施与验收

1. 开发服务器编译、类型检查和单元测试；隔离 CI 验证迁移、权限、幂等并发、报表和浏览器。
2. 业务确认矩阵、关键服务粒度、日历及可承诺时限；每组任命独立主管，准备至少两名配置管理员。
3. 按既有发布流程备份，执行迁移 037；一批完整功能后发布，避免每个小修改部署。
4. 试点个人问题、局部中断、核心生产中断、误报降级、重复升入 P1、跨组交接、人员离职、AI 不可用、通知失败。
5. 验证员工不能伪造等级；负责人只可直接升级；P1 不自审；配置不自批；降级超时仍在；重试不重复变更。
6. 技术通过、真实人员任命、真实通知送达、业务 SLA 承诺分别验收。

观察指标：自动判定纠正比例、P1 误报率、确认耗时、调级原因、升级前后超时率、缺独立主管的组数。指标用于改善规则，不按低等级占比考核工程师。
